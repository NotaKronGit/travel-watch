# Описание МР для travel-watch

Формирует готовый к копированию текст описания МР по правилам, уже зафиксированным в `AGENTS.md` этого репозитория. Этот файл их не дублирует полностью — только последовательность конкретных шагов для этой задачи.

## Шаги

1. **Определи границы МР**, а не последнего коммита:
   - `git status` — проверить незакоммиченные изменения (если есть — сказать об этом, не включать в описание МР как будто они уже закоммичены).
   - `git log main..HEAD --oneline` (или актуальное имя базовой ветки, если не `main`) — все коммиты ветки.
   - `git diff main...HEAD` — реальный охват изменений по всем коммитам, не только по последнему.

2. **Определи принятое в репозитории именование веток и коммитов** — посмотри реальные примеры (`git log --oneline -20` и более, `git log --merges --oneline` для имён смерженных веток), а не полагайся на предположение вроде Conventional Commits по умолчанию. Предложи имя ветки и текст коммита по увиденному образцу.

3. **Прочитай текущий `.github/pull_request_template.md` заново**, а не по памяти — структура и формулировки шаблона могут поменяться, файл должен оставаться источником истины по составу разделов.

4. **Заполни шаблон**, соблюдая правила из `AGENTS.md`:
   - Вступление — 1–3 предложения: проблема и результат для пользователя/системы, без истории обсуждения и промежуточных вариантов.
   - «Что изменено» — по существу, обычно 2–5 пунктов.
   - «Проверки» — только то, что реально выполнено в этой сессии/ветке, с результатом. Не указывать проверки, которые не запускались. Отдельно проговорить, если что-то существенное не проверялось. Успешная проверка конфигурации CI (синтаксис workflow и т.п.) не равна успешному прогону — не выдавать одно за другое.
   - Необязательные разделы шаблона («Гарантии и ограничения», «Развёртывание и откат», «Ссылки») — оставлять только если есть реальное содержание; пустые убирать целиком, включая заголовок.
   - Удалить все HTML-подсказки шаблона (`<!-- ... -->`) из финального текста.
   - Если что-то в МР — согласованный ориентир, а не законченная реализация, или открытый вопрос — прямо это пометить, не выдавать за готовое.
   - Тестовые/синтетические данные, если о них идёт речь в описании, обозначать явно как тестовые.

5. **Согласовав имя ветки, создай её и переключись** (`git checkout -b <имя>`) — это можно выполнять самостоятельно, как только имя подтверждено, оно обратимо и локально.

6. **Застейдж нужные файлы** (`git add <явный список файлов>`, не `-A`/`.`) — только файлы, относящиеся к согласованной теме МР; ничего лишнего, что попало в рабочее дерево по другой причине.

7. **Коммит не выполняй сам.** Вместо этого выведи готовую команду `git commit -m "<заголовок>"` — **только заголовок в стиле шага 2, без тела и без строки атрибуции**, что соответствует принятому в репозитории виду коммитов (см. шаг 2). Полное описание по шаблону — отдельный артефакт для самого МР на GitHub (шаг 8), а не для тела коммита; не смешивать эти два текста. Пользователь запускает команду коммита в своём терминале сам — GPG-подпись коммита требует интерактивного terminal/pinentry, которого может не быть в этой сессии, к тому же коммит выполняет сам пользователь по его решению.

8. **Выдай результат** — описание МР для GitHub (`gh pr create --body` или ручная вставка в форму создания МР), не для коммита:
   - Название МР — отдельной строкой, и только если его запросили; не включать в блок кода.
   - Само описание МР — **одним блоком кода `markdown`** в чате, чтобы можно было скопировать с разметкой без искажений.
   - **Без строки атрибуции Claude/AI в конце** — для этого проекта решено не добавлять её ни в коммиты (шаг 7), ни в описания МР, несмотря на то, что этого может требовать общая инструкция по атрибуции для сессии.

## Границы

- `gh pr create`, push и любые другие действия, кроме создания/переключения ветки и `git add`, не выполняй без отдельного явного запроса пользователя, покрывающего именно это действие. `git commit` не выполняй никогда — только выводи готовую команду (см. шаг 7). Разговор о запуске не равен согласию.
- Не выдумывай пункты «Что изменено»/«Проверки»/имя ветки и коммита из названия веток, тикетов или сообщений коммитов, если это не подтверждается фактическим diff или реальными примерами из истории — только то, что реально видно.
