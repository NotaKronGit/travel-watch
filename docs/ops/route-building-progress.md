# Автоматическое построение маршрутов и история

Новая заявка проходит `queued` → `building` → `awaiting_schedules` либо `no_routes`/`failed`. Это построение схем до проверки временной совместимости. Вся заявка после успешного построения не завершается. Контракт и гарантии — [ADR 0010](../adr/0010-route-building-progress.md).

## Локальный запуск

После обновления кода примените миграции обеих БД и создайте топики:

```sh
make migrate
make search-migrate
make kafka-up
```

Нужен [каталог аэропортов Search](airport-catalog.md) и настроенный `COLLECTOR_YANDEX_API_KEY` в локальном `.env`. Ключ не добавлять в Git. В отдельных терминалах, дополнительно к Cabinet, его отправителю outbox и потребителю Search:

```sh
make search-build-routes
make search-publish-progress
make cabinet-consume-progress
```

Создайте новую заявку. В списке и карточке этап обновляется автоматически. В карточке появится история с длительностью и числом схем. Существующие заявки не переотправляются и не строятся миграцией. Статическая секция сравнения экспериментальных маршрутов пока остаётся отдельной от результата этой заявки.

## stage_local

Сначала обновите стенд (`make stage-local-up`). Он запускает отправителя прогресса, потребителя Cabinet и создаёт отдельный топик. При обновлении с предыдущей версии предварительно выполните `make stage-local-stop`: старый потребитель Search не должен подтверждать новые создания без очереди построения.

В `.env.stage_local` настройте `COLLECTOR_YANDEX_API_KEY`. Каталог аэропортов в этой БД независим от каталога локальной разработки:

```sh
make stage-local-airports-sync
make stage-local-building-up
```

Вторая команда включает обработчик с профилем `planning`. Внешние запросы начнутся для новых необработанных заданий. Стандартный запуск без профиля оставляет их в очереди. Образ Search содержит бинарник и конфигурацию Collector; ключ передаётся только обработчику через окружение.

В dev после публикации новых образов и `make dev-up` аналогичные команды — `make dev-airports-sync` и `make dev-building-up`, ключ берётся из `.env.dev`. Старые образы этих команд не поддерживают. Публикация и удалённый запуск в рамках этого изменения не выполняются.

## Конфигурация и восстановление

`progress` в YAML каждого сервиса содержит настройки Kafka и таймаутов; переопределения — `SEARCH_PROGRESS_*` и `CABINET_PROGRESS_*`. Топик должен совпадать у отправителя, потребителя и инициализации Compose (`ROUTE_BUILDING_TOPIC`). По умолчанию опрос 2 секунды, внешняя/DB-операция 10 секунд, аренда задания 10 минут, максимум 3 попытки после аварий. Лимит построения — `planner.timeout` (8 минут), он должен быть меньше аренды с запасом на операции БД.

`route_building` в Search хранит этап, попытку и результат; `progress_outbox` — историю переходов и состояние доставки. `trip_stage_history` в Cabinet хранит полученные переходы. Эти таблицы читаются только своим сервисом. Обработчики нескольких экземпляров захватывают разные задания; общего распределённого лимита квоты Яндекса пока нет, поэтому для первого запуска используйте один обработчик.

При недоступности Kafka этап сохраняется в Search, а интерфейс обновится после восстановления доставки. Ошибка источника или таймаут видны как ошибка этапа, а не отсутствие маршрутов. При остановке процесса задание восстанавливается после аренды. Отмена проверяется периодически и всегда повторно при записи результата; уже отправленный HTTP-запрос может успеть выполниться до получения отмены.

Ошибка этапа не перезапускается автоматически. Команда ручного повторения — следующий отдельный шаг; не очищайте таблицы истории или inbox ради повтора.

## Проверки и откат

`make check`, `make test-int` и браузерный сценарий `frontend/e2e/progress.spec.ts` работают без реального Яндекса. Интеграционные тесты используют временные схемы PostgreSQL. Проверены атомарность создания/события, повторная доставка, устаревшая аренда, отмена, порядок проекции и сохранение черновика при фоновом обновлении.

`make test-progress-e2e` проверяет всю цепочку настоящих процессов: создание через HTTP Cabinet → outbox → Kafka → Search → построение → outbox → Kafka → история и этап в HTTP API Cabinet. Подменён только транспортный провайдер: управляемый дочерний процесс отвечает по протоколу Collector, удерживает ответ до разрешения теста и использует синтетические аэропорты. Яндекс, Gemini и загрузки справочников не вызываются.

Проверяются переходы очереди/построения/ожидания расписаний, число схем и сохранённая длительность, повтор точного события с ожиданием подтверждения offset, отмена и запоздавшее событие, принудительное завершение процесса построения и восстановление во втором процессе. Для восстановления тест действительно ждёт минутную аренду; даты в БД не подменяются. Обычный прогон занимает около 80 секунд на локальном окружении с прогретой сборкой; большая часть — ожидание аренды.

Нужны локальные Cabinet/Search PostgreSQL и роли из `.env`, как для `make test-int`. Тест сам собирает бинарники, создаёт отдельные случайные схемы в обеих БД и отдельные топики выделенного тестового Kafka на порту 19092; после завершения останавливает свои процессы и удаляет свои схемы/топики. Рабочие заявки и процессы не затрагиваются. Этот тест добавлен в job `integration` после тестов Kafka.

Миграции: Search 00003 и Cabinet 00010. Перед откатом остановить новых обработчиков и согласовать судьбу накопленных заданий/событий. Down удаляет результаты и историю этапов. Откат приложения без миграций не возобновляет обработку; старый Search принимает создания без новой очереди, поэтому его нельзя оставлять работающим в смешанной версии.
