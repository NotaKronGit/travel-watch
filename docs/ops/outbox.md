# Отправитель outbox Cabinet

`cabinet publish-outbox` — отдельный процесс того же бинарника с ролью `cabinet_app`. HTTP Cabinet сохраняет заявку и событие одной транзакцией и не подключается к Kafka. Контракт и гарантии описаны в [ADR 0004](../adr/0004-trip-request-outbox.md).

## Запуск

После `make db-up` и `make migrate` запустите локальную Kafka и отправитель:

```sh
make kafka-up
make publish-outbox
```

Процесс читает `.env` и YAML так же, как `make cabinet`. Для нескольких брокеров env содержит адреса через запятую: `broker-a:9092,broker-b:9092`. Остановка — Ctrl+C или SIGTERM. Команда работает в переднем плане; `make kafka-up` поднимает брокер и идемпотентно создаёт топик. `make kafka-stop` останавливает брокер, сохраняя том. В stage_local и dev отправитель запускается контейнером `outbox`. Сейчас поддерживается Kafka без TLS/SASL в доверенном локальном окружении.

## Настройки

Блок `outbox` в `services/cabinet/config.yaml`:

| Параметр | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `brokers` | `[127.0.0.1:9092]` | Начальные адреса Kafka |
| `topic` | `travelwatch.trip-requests.v1` | Топик событий |
| `poll_interval` | `1s` | Пауза при пустой очереди или ошибке |
| `db_timeout` | `5s` | Таймаут каждой операции БД |
| `publish_timeout` | `10s` | Таймаут попытки отправки |
| `lease_duration` | `30s` | Срок захвата записи |
| `retry_min` / `retry_max` | `1s` / `1m` | Границы экспоненциальной задержки |

Срок аренды должен превышать таймаут публикации плюс два таймаута БД. Все интервалы — от 1ms до 24h. Env-переопределения используют префикс `CABINET_OUTBOX_`. Настройки Kafka не обязательны для HTTP-режима.

## Обработка и диагностика

Один процесс берёт одну запись через `FOR UPDATE SKIP LOCKED` и записывает срок аренды с новым токеном. Сетевая отправка выполняется после завершения SQL-запроса. Подтверждение и перенос повтора принимаются только с текущим токеном. При падении процесса или ошибке записи результата событие становится доступным после истечения аренды.

Тип Protobuf передаётся в Kafka header `event_type`; правила отмены и обновления описаны в [ADR 0005](../adr/0005-trip-lifecycle.md).

Kafka-клиент `kafka-go` отправляет синхронно с `acks=all`, одной попыткой на вызов и ключом UUID заявки. Повторами управляет outbox. Автоматическое создание топика выключено. Ошибка, таймаут или отмена не доказывают отсутствие записи в Kafka: допускаются дубли с прежними event_id и payload. В БД событие отмечается опубликованным только после успешного ответа. Search пока отсутствует.

При остановке текущий запрос отменяется; незавершённая запись остаётся под арендой. Закрытие клиента дожидается начатых сетевых операций, ограниченных таймаутами Kafka-клиента. Счётчик attempts включает захваты, после которых процесс мог упасть до отправки. Повторы не ограничены по числу попыток. Логи не содержат payload и сырые ошибки подключения; `last_error` содержит безопасный маркер `publish_failed`.

Проверить очередь в PostgreSQL Cabinet:

```sql
SELECT count(*) FILTER (WHERE published_at IS NULL) AS pending,
       count(*) FILTER (WHERE published_at IS NOT NULL) AS published,
       min(created_at) FILTER (WHERE published_at IS NULL) AS oldest_pending
FROM outbox_events;

SELECT id, attempts, available_at, lease_until, last_error
FROM outbox_events WHERE published_at IS NULL
ORDER BY created_at LIMIT 20;
```

`make check` проверяет ветви отправки на подменённом Publisher; `make test-int` проверяет аренды, конкурирующих отправителей, повторы и подтверждения в PostgreSQL. `make test-kafka` проверяет доставку с настоящим брокером, остановку и восстановление Kafka, потерю подтверждения БД после отправки, неизменность повторного сообщения и сохранность сообщений при перезапуске брокера. Автоматической очистки опубликованных записей пока нет.


## Локальные окружения и CI

Общий файл `deploy/compose/kafka.yaml` задаёт Apache Kafka 4.1.2, один узел KRaft, постоянный том и retention 168 часов. Репликация и min.insync.replicas равны 1; `acks=all` здесь означает подтверждение единственного брокера и не защищает от потери его диска. Настройки подходят для разработки. Создание топика не изменяет параметры уже существующего топика.

Для Go на хосте Kafka доступна на `127.0.0.1:9092`; внутри Compose используется `kafka:9092`. Stage_local и dev не публикуют Kafka наружу: сеть `events` внутренняя, доступ к ней есть у брокера, одноразового `kafka-init` и `outbox`. HTTP Cabinet не зависит от готовности Kafka. При первом запуске отправитель ждёт миграции и создание топика; после старта недоступность брокера обрабатывается повторами. Готовность процесса outbox в Compose не доказывает доставку — проверяйте очередь SQL-запросами выше.

Каждый проект Compose имеет собственный том `kafka_data`; остановка и перезапуск его не удаляют. `down -v` удалит данные выбранного окружения. В `.env.stage_local`/`.env.dev` можно задать `CABINET_OUTBOX_TOPIC`: одинаковое значение передаётся в инициализатор и отправитель. Остальные настройки отправителя меняются через смонтированный YAML или явные `environment` Compose.

`make test-kafka` требует локальную PostgreSQL из `.env`, создаёт отдельную схему с синтетическими городами и отдельный брокер `travel-watch-kafka-test` на `127.0.0.1:19092`. Он останавливает только этот тестовый брокер; не запускайте два таких теста одновременно. После теста схема и случайный тестовый топик удаляются. Брокер остаётся запущенным для повторного прогона; остановить его можно командой:

```sh
docker compose -p travel-watch-kafka-test -f deploy/test/compose.yaml stop
```

Обычные `make check` и `make test-int` не запускают Kafka. Отдельный шаг GitHub Actions вызывает `make test-kafka` и удаляет тестовое окружение после проверки. Тест не скачивает GeoNames. Конфигурация CI проверена локально; это не подтверждает выполнение workflow на GitHub.
