# Запуск Search

Search принимает события заявок из Kafka и сохраняет их в своей PostgreSQL-базе. Поиск предложений ещё не запускается. [Гарантии и ограничения](../adr/0006-search-inbox.md).

## Локально

Добавьте в `.env` два разных пароля `SEARCH_DATABASE_OWNER_PASSWORD` и `SEARCH_DATABASE_APP_PASSWORD` по образцу `.env.example`.

```sh
make db-up
make search-db-init
make search-migrate
make kafka-up
```

В отдельных терминалах запускаются `make publish-outbox` и `make search`. Cabinet запускается обычной командой `make cabinet`. Создайте новую заявку в кабинете, затем проверьте данные:

```sh
docker compose --env-file .env -f deploy/compose/compose.yaml exec postgres \
  psql -U search_owner -d search -c \
  "SELECT request_id,status,created_at,cancelled_at,received_at FROM search_requests ORDER BY received_at DESC LIMIT 20"

docker compose --env-file .env -f deploy/compose/compose.yaml exec postgres \
  psql -U search_owner -d search -c "SELECT count(*) FROM inbox_events"
```

После отмены заявки состояние в Search становится `cancelled`. В Cabinet сохранённая заявка остаётся `saved`, пока следующий этап не начнёт фактическую работу.

## Конфигурация

[services/search/config.yaml](../../services/search/config.yaml) обязателен. Путь задаёт `SEARCH_CONFIG`. Приоритет: env процесса → корневой `.env` → YAML. Viper проверяет неизвестные ключи и типы; все поля переопределяются через префикс `SEARCH_`, например `SEARCH_CONSUMER_GROUP_ID`, `SEARCH_CONSUMER_BROKERS`, `SEARCH_DATABASE_PORT`.

`migrate` использует только пароль владельца, `consume` — приложения. Брокеры задаются списком YAML или строкой env с запятыми. `consumer` содержит topic, group_id, таймауты БД, подключения и подтверждения Kafka. Локальные Kafka-соединения без TLS; публичное развёртывание пока не подготовлено.

## Stage_local и dev

Добавьте два пароля Search в соответствующий `.env.stage_local`/`.env.dev`. `make stage-local-up` собирает Search, `make dev-up` скачивает его образ с тем же IMAGE_TAG, что Cabinet и frontend.

Порядок зависимостей: PostgreSQL → `search-db-init` → `search-migrate` → `search`; потребитель также ждёт `kafka-init`. Одноразовые контейнеры штатно завершаются с кодом 0. Отдельного HTTP endpoint у Search нет; `up --wait` подтверждает запуск процесса, а получение события проверяется запросом к БД и логами `search`.

`search-db-init` добавляет роли и базу на существующем томе без удаления данных Cabinet. Повторный запуск не меняет пароли уже существующих ролей. Для смены пароля нужна отдельная операция PostgreSQL. Системный пароль PostgreSQL передаётся только одноразовому контейнеру инициализации, не приложению Search.

Новый Compose dev требует публикации образа Search; старый dev-latest до этого МР его не содержит. Не запускайте обновлённый dev до успешной публикации всех трёх образов.

Для остановки только потребителя:

```sh
docker compose --env-file .env.stage_local -f deploy/stage_local/compose.yaml stop search
```

Остановка не удаляет БД и offsets. Откат образа не откатывает миграции. Не удаляйте inbox или записи отмены для повторной обработки.

## Проверки

`make check` включает unit-тесты конфигурации, разбора событий и порядка подтверждения. `make test-int` проверяет миграции и транзакции Search в изолированной схеме своей БД; предварительно нужен `make search-db-init`.

`make test-kafka` последовательно проверяет Cabinet и Search на отдельном тестовом брокере. Search использует случайные топик, группу и схему; проверяет потерю подтверждения после записи БД, повтор после перезапуска, дубли, позднее создание после отмены и сохранённые offsets. Тесты не скачивают справочник и не используют поставщиков билетов.

## Сравнение GraphPlanner и Gemini

`make search-compare` запускает пять синтетических направлений: Иваново → Паттайя, Казань → Сочи, Тверь → Дубай, Омск → Стамбул, Токио → Гонолулу. PostgreSQL, Kafka и пароли БД не требуются. Это отдельный эксперимент, не обработка пользовательских заявок.

Создайте ключ в [Google AI Studio](https://aistudio.google.com/apikey) и добавьте в локальный корневой `.env`:

```dotenv
SEARCH_GEMINI_API_KEY=your-api-key
```

Затем:

```sh
make search-compare
```

По умолчанию используется `gemini-3.5-flash-lite`. У модели есть [Free tier](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.5-flash-lite); доступность и квоты зависят от проекта и региона. Для бесплатного эксперимента используйте проект Free tier. Приложение не определяет тариф аккаунта и не гарантирует бесплатность платного проекта. Отправляются только синтетические топология и запрос направления; аккаунты пользователей, комментарии, реальные заявки не передаются.

Секция `gemini` в YAML задаёт модель, таймаут 30 секунд, максимум 1024 выходных токена, пределы тела запроса 32 KiB и ответа 64 KiB. Env: `SEARCH_GEMINI_MODEL`, `SEARCH_GEMINI_TIMEOUT`, `SEARCH_GEMINI_MAX_OUTPUT_TOKENS`, `SEARCH_GEMINI_MAX_REQUEST_BYTES`, `SEARCH_GEMINI_MAX_RESPONSE_BYTES`. Ключ хранится только локально; URL Google фиксирован, перенаправления запрещены.

За запуск выполняется не более пяти последовательных запросов без автоматических повторов. При 429 проверьте квоту в AI Studio и повторите позже. Лимит токенов ограничивает ответ каждого запроса, а не весь тариф аккаунта. Обрезанный ответ считается ошибкой; неполный ответ не становится успешным пустым поиском.

JSON-отчёт показывает пересечение кандидатов, различия, ошибки каждой стороны, длительность планирования с валидацией и число собранных поездок. `reported_usage` — суммарные счётчики токенов из полученных ответов API, не счёт за использование; при сбое сети часть расхода может остаться неизвестной. Денежную стоимость смотрите в кабинете провайдера. Ошибки кейсов дают ненулевой код выхода после печати отчёта. Диагностика Gemini показывает HTTP-статус и выбранные поля JSON-ошибки Google: `code`, `status`, `message`, а также `reason` из ErrorInfo. Сообщение ограничено 1000 символами; ключ маскируется, управляющие символы удаляются. Сырое тело, заголовки и metadata не выводятся. Для сетевых ошибок различаются `timeout`, `cancelled`, `dns_error`, `connect_error`, `connection_closed` и `transport_error`; `phase` показывает ожидание заголовков (`request_before_response_headers`, включая подключение и отправку) либо чтение тела (`response_body`). Это не измерение времени работы модели. Ошибка не означает отсутствие маршрута.

LLM выбирает индексы существующих связей; общий валидатор отклоняет выдуманные или недопустимые пути. Полнота LLM всегда неизвестна, даже при совпадении с GraphPlanner. Расписания и допустимость стыковок проверяет Go. Пять совпадений на синтетических данных не доказывают качество на реальных перевозках.

`make check` проверяет HTTP-адаптер на локальном тестовом сервере, включая пять направлений, некорректные ответы, лимиты, таймаут и запрет перенаправления. Реальный Gemini в CI не вызывается. Для оценки качества нужен отдельный прогон с ключом.

### Первый реальный прогон, 2026-09-15

Google отклонил генерацию через `gemini-2.5-flash-lite` с 404: модель больше недоступна новым пользователям. По рекомендации API модель по умолчанию заменена на `gemini-3.5-flash-lite`.

В двух прогонах по пять направлений успешны по два кейса: в первом Казань → Сочи и Омск → Стамбул, во втором Омск → Стамбул и Токио → Гонолулу. Успешные кандидаты и собранные поездки совпали с GraphPlanner. Во втором прогоне Иваново и Тверь достигли таймаута 30 секунд, Казань получила HTTP 403; причина 403 не установлена. Это ошибки выполнения, не доказательство отсутствия маршрута или плохого качества модели.

API сообщил 2005 и 1132 токена соответственно; расход незавершённых запросов неизвестен. Стабильность доступа и полное сравнение пяти направлений остаются открытыми. Ключ в проект не сохранён.

### Сохранение локального отчёта

```sh
make search-compare > /tmp/search-compare.log 2>&1
```

Файл содержит JSON-отчёт и сообщения завершения процесса. Подробности находятся в `reports[].alternative.error`. Исторические ответы, ранее отброшенные адаптером, восстановить невозможно; подробная диагностика появляется только в новых запусках. Не включайте трассировку HTTP-заголовков с API-ключом.

После добавления подробной диагностики повторный прогон завершился успешно на всех пяти направлениях: 9 общих кандидатов (5 + 1 + 1 + 1 + 1), без различий с GraphPlanner, совпало число собранных поездок. Запросы заняли 0,85–1,33 секунды каждый; API сообщил 3007 входных и 127 выходных токенов, всего 3134. Таймаут и параметры генерации не увеличивались. Ошибка 403 не повторилась, её историческая причина остаётся неизвестной. Один успешный прогон не подтверждает стабильность сервиса.
