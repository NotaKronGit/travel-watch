# GitHub Actions: проверки и сборка

Workflow `ci.yml` запускается на PR и push в `main`. Проверки выполняются параллельно на отдельных GitHub-hosted runners:

- `checks`: формат Go, воспроизводимость Protobuf, golangci-lint/gosec, Go-тесты с race detector, типизация/сборка frontend и frontend-тесты, проверка Compose.
- `integration`: отдельная PostgreSQL, миграции, `make test-int`, затем `make test-kafka` с тестовым брокером.
- `browser`: отдельная PostgreSQL и Cabinet, установка headless Chromium, браузерные тесты. Kafka этому job не нужна.

Установка зависимостей, инструментов и выполнение тестов разделены на шаги, чтобы по времени шага было видно, что именно замедляет CI. Локальная команда `make check` остаётся без изменений; в CI её проверки запускаются отдельными командами.

## PR

Одновременно с проверками `images-pr` вызывает `build-images.yml`: Cabinet и frontend собираются параллельно для `linux/amd64` и `linux/arm64`. Образы PR не публикуются, разрешения на запись пакетов не выдаются.

Итоговый job `test` ждёт `checks`, `integration`, `browser` и обе сборки PR. Любая ошибка, отмена или пропуск обязательного job не позволяет ему завершиться успешно. Имя `test` сохранено для существующего required status check. Если в настройках репозитория были отдельно обязательны прежние имена matrix-сборок, их нужно заменить на `test`.

При новом push в тот же PR предыдущий workflow отменяется. Параллельная сборка может потратить время runner даже при ошибке тестов; это компромисс ради более короткого ожидания результата.

## Main и публикация

При push в `main` сначала завершаются проверки и итоговый `test`. Затем job `images` вызывает тот же `build-images.yml` с публикацией SHA-тегов в GHCR. После успешной публикации обоих образов `dev-latest` обновляет их теги без пересборки. Публикация недоступна для PR и не запускается при провале проверок. Новые push в main не отменяют текущую публикацию.

## Кэш и инструменты

- `setup-go` и `setup-node` сохраняют кэши Go и npm; `npm ci` продолжает устанавливать зависимости по lock-файлу.
- Buf 1.61.0 устанавливается готовым бинарником через `buf-setup-action`, без сборки Buf из исходников.
- Playwright устанавливает Chromium с `--only-shell`: текущие тесты используют стандартный headless-режим. Для другого browser channel или headed-режима набор установки нужно пересмотреть.
- Docker-слои сохраняются через `type=gha` с отдельным scope для каждого образа.
- Компиляция Go использует BuildKit cache mount. `actions/cache` и закреплённый по SHA `buildkit-cache-dance` переносят его между runners; обычный экспорт слоёв этот mount не сохраняет. Ключ зависит от ОС/архитектуры runner, go.mod/go.sum, Dockerfile и SHA коммита; предыдущий кэш совместимых зависимостей восстанавливается по префиксу. Go проверяет содержимое исходников и выбирает подходящие записи кэша для каждой целевой архитектуры.
- Go-тесты и frontend-тесты исключены из Docker-контекста. Frontend Dockerfile копирует только файлы, нужные для сборки приложения; тесты по-прежнему проверяются на полном checkout в jobs проверок.

Кэш — оптимизация, сборка должна работать и без него. Холодный кэш, очередь runners, сеть и перенос самого кэша влияют на время; ускорение оценивается по реальным прогонам GitHub, а не по локальному времени Docker.

## Локальная проверка изменений CI

Проверить workflow можно actionlint. Изменения Dockerfile проверяются сборкой обоих образов для обеих архитектур без push. Успешная локальная проверка не подтверждает запуск Actions, восстановление GitHub-кэша или публикацию в GHCR.
