# stage_local: весь кабинет в Docker

Stage_local позволяет проверить собранное приложение без запуска Go, Node.js и Vite на хосте. Нужен только работающий Docker с Compose v2. Это локальное окружение с HTTP, не публичный сервер.

## Запуск

Из корня проекта скопируйте `deploy/stage_local/.env.example` в `.env.stage_local`, если файл ещё не создан. Задайте отдельные пароли для этого окружения.

```sh
make stage-local-up
```

Команда собирает Cabinet и frontend, запускает PostgreSQL и Kafka, применяет миграции, создаёт топик и запускает отправитель outbox. Команда ждёт готовности приложения. Откройте [http://localhost:18080](http://localhost:18080).

Порядок запуска задаёт `depends_on` в Compose: миграции ждут готовности PostgreSQL (`service_healthy`), Cabinet — успешного завершения миграций (`service_completed_successfully`), frontend — готовности Cabinet. Makefile вызывает одну команду `docker compose up --build -d --wait --wait-timeout 120`. Флаг `--wait` ждёт готовности стенда перед завершением команды.

Frontend раздаётся Nginx и проксирует API к Cabinet. Наружу опубликован только порт frontend, привязанный к 127.0.0.1. База не публикует порт и работает в отдельной внутренней Docker-сети. Роль приложения не имеет прав миграций; миграция запускается отдельным одноразовым контейнером.

Контейнер `kafka-init` создаёт топик и также штатно завершается с кодом 0. Отправитель ждёт его и миграции; HTTP Cabinet не зависит от брокера. Kafka хранится в отдельном томе `travel-watch-stage-local_kafka_data` и не публикует порт наружу. [Команды проверки очереди и гарантии](outbox.md).

После успешных миграций контейнер `migrate` остаётся в состоянии `Exited (0)` — это нормально. При следующем `stage-local-up` он запускается снова; Goose применяет только новые миграции.

Том `travel-watch-stage-local_postgres_data` независим от dev-тома. Его данные сохраняются при повторном запуске и остановке:

```sh
make stage-local-stop
make stage-local-restart
make stage-local-logs
```

`make stage-local-stop` останавливает стенд, `make stage-local-restart` перезапускает существующие контейнеры PostgreSQL, Kafka, outbox, Cabinet и frontend, а `make stage-local-logs` показывает логи приложения. Перезапуск не пересобирает образы и не применяет изменения конфигурации.

Для обновления после изменения кода или конфигурации снова выполните `make stage-local-up`. Если миграция не проходит, команда прекращается до запуска новой версии приложения. Автоматического отката миграций нет.

Dev и stage_local на localhost используют одинаковое имя cookie: вход в одном окружении может заменить cookie другого. Проверяйте их в разных профилях браузера или завершайте сессию перед переключением. Серверы не принимают сессии чужой БД.

## Справочник городов

После первого запуска или очистки базы загрузите справочник именно в stage_local:

```sh
make stage-local-cities-sync
```

Команда собирает актуальный образ Cabinet и запускает одноразовый контейнер импорта с настройками `.env.stage_local`. Он ждёт PostgreSQL и миграции, имеет доступ к базе и интернету, затем удаляется. Повторный запуск обновляет справочник. После входа страница создания заявки доступна по `/#/trips/create`; без загруженного справочника подсказки будут пустыми. Обычный `stage-local-up` импорт не запускает: контейнер находится в профиле `tools`.

`make cities-sync` относится к другой базе — локальной из `.env`. Описание данных, русских названий и ограничений — в [инструкции импорта](city-catalog.md).

## Браузерная проверка контейнеров

При установленных frontend-зависимостях и Chromium:

```sh
PLAYWRIGHT_BASE_URL=http://localhost:18080 npm --prefix frontend run test:e2e
```

Тесты обращаются к контейнерам, Vite не запускается. Создаётся тестовый аккаунт в БД stage_local.

## GitHub Actions

`.github/workflows/ci.yml` выполняется для PR и push в main:

- Проверяет Go (включая golangci-lint и gosec через `make check`), frontend, контракт API, миграции, доставку outbox с отказами Kafka и браузерный сценарий.
- После тестов собирает образы Cabinet и frontend для linux/amd64 и linux/arm64.
- Стадии Go и Node/Vite выполняются на `BUILDPLATFORM`: Go кросс-компилирует через `TARGETOS`/`TARGETARCH`, frontend собирается в общую статику. Компиляция не требует QEMU; финальные образы остаются для целевой архитектуры. QEMU в workflow оставлен для команд в финальном Alpine-образе, например установки сертификатов.
- При push в main публикует образы `ghcr.io/<owner>/<repo>/cabinet:<commit-sha>` и `frontend:<commit-sha>`. Используется встроенный GITHUB_TOKEN с packages:write; личный токен в репозиторий не нужен.
- После публикации обоих образов обновляет их тег `dev-latest`. Запуск готовой версии описан в [инструкции dev](dev-images.md).

Stage_local собирает образы из текущих локальных файлов. GitHub-hosted runner не имеет доступа к вашему компьютеру и не обновляет его автоматически. На этом этапе локальный деплой запускается командой Make; workflow удалённого деплоя, SSH, Ansible и Kubernetes не добавлены.

Публикация образов фактически ещё не выполнялась: файлы нужно закоммитить, открыть PR и пройти проверки. В настройках репозитория рекомендуется сделать job `test` обязательным для merge.
