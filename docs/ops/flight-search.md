# Эксперимент: Google Flights через Fli

Реализованы `flights.Provider` внутри Collector, адаптер Fli и ручная команда `flights-find`. Яндекс и существующий `transport-stdio` не заменяются. Наш автоматический планировщик использует адаптер как дополнительный источник схем; Gemini пока не вызывает этот инструмент. Результаты планировщиков друг другу не передаются.

Fli — сторонняя библиотека, работающая с неофициальным интерфейсом Google Flights, не официальный API Google. Используется опубликованная версия `flights==0.9.0` (MIT). На момент проверки 0.10.0 присутствует в main upstream, но отсутствует в PyPI. [Проект и ограничения](https://github.com/punitarani/fli).

## Запуск

Из корня проекта; нужен Python >=3.10:

```sh
make flights-setup FLI_PYTHON=python3.12
make flights-find ARGS='-from IST -to BKK -date 2026-10-15 -adults 2 -limit 5 -nonstop'
```

Дата обязательна, локальная в аэропорту отправления. Для будущих запусков задавайте актуальную дату. Без `-nonstop` допускаются варианты со стыковками. Вход принимает IATA конкретных аэропортов, не произвольные города.

Настройки находятся в `services/collector/config.yaml`, секция `fli`: `python`, `bridge`, `timeout`, `max_response_bytes`. Env: `COLLECTOR_FLI_PYTHON`, `COLLECTOR_FLI_BRIDGE`, `COLLECTOR_FLI_TIMEOUT`, `COLLECTOR_FLI_MAX_RESPONSE_BYTES`. YAML можно выбрать через `COLLECTOR_CONFIG`. Ключ Яндекса для этой команды не нужен; ключи API и биллинг для Fli не использовались.

Go запускает отдельный Python-процесс на запрос с общим deadline (45 секунд по умолчанию), ограничивает его stdout (1 MiB), не передаёт окружение с секретами и не выводит stderr библиотеки. Fli имеет собственный HTTP timeout 15 секунд и ограниченные внутренние повторы. Для запуска из исходников Python и Fli устанавливаются вручную в игнорируемую `.local/fli-venv`. Образ Search содержит Python/Fli и мост; его runtime основан на Debian slim для совместимости с curl-библиотекой. Это дочерний процесс Collector, не новый постоянно работающий сервис. Unit-тесты не устанавливают Fli и не обращаются к сети.

## Результат и границы

- Источник `google-flights-fli`, исходный запрос, время наблюдения, варианты с упорядоченными перелётами и длительностью в минутах.
- Время отправления и прибытия — **локальные строки без подтверждённого UTC-смещения**. Нельзя сравнивать их как UTC; следующий этап должен разрешить timezone каждого аэропорта и учесть смену аэропортов.
- Цена, багаж, тариф и доступность бронирования пока не нормализуются. Бронирование не вызывается.
- Всегда `complete=false`: Fli не гарантирует полноту покрытия и может пропускать строки при частичных ошибках разбора. `limit_reached` означает усечение полученной выдачи.
- Пустой результат означает только отсутствие распознанных предложений на конкретный запрос. Он не доказывает отсутствия сообщения между городами.
- Ошибки, неподдерживаемые коды, лимит поставщика и отмена отделены от успешного пустого ответа. Go проверяет соответствие аэропортов, даты и числа участков запросу.

## Проверки без сети

`go test -race ./services/collector/...` проверяет контракт, конфигурацию, соответствие результата запросу, ошибки протокола, таймаут и пустой ответ. Тестовый исполняемый файл заменяет Python-процесс; CI не устанавливает Fli и не обращается к Google. Реальная совместимость Python-библиотеки проверена только ручными запросами выше.

## Автоматическое построение схем

`planner.google_flights.enabled: true` в Search включает дополнительную фазу поиска по уже выбранным аэропортам отправления/хабам и аэропортам назначения. Яндекс продолжает свой поиск. `max_requests: 30` ограничивает число запросов Google Flights отдельно от бюджета Яндекса, `max_options: 20` — размер ответа на одну пару и дату. Общий timeout и предел кандидатов прежние. Запросы остаются последовательными, но выполняются проходами по датам: разные пары проверяются прежде повторных дат. Сначала каждый аэропорт отправления получает пару с первым аэропортом назначения, затем со вторым. Аэропорты отправления чередуются по municipality/стране/региону из каталога; отсутствующий municipality не объединяет аэропорты. Это приближение, а не полная модель городских агломераций. Пустая первая дата не исключает пару из следующих проходов. Число запросов не превышает прежний бюджет.

Из диапазона заявки берутся начало, середина (округление к началу) и конец без повторов: максимум три даты. Дата нужна только API поставщика. `flight-paths` передаёт в Search **только цепочки аэропортов**, без цен, номеров рейсов и времени отправления/прибытия. Разные предложения с одной цепочкой сводятся к одной схеме в пределах пары и набора дат. В шагах сохраняются `evidence=google-flights-fli` и `observed_dates`; в результате — `flight_checks` с запрошенными парами/датами и исходами. Переезды при смене аэропортов помечаются как предполагаемые.

Цепочки, уже найденные Google Flights (например, DME → CAI → SSH), принимаются целиком. Наш собственный расширенный перебор авиационных цепочек ещё не реализован. Железнодорожный/авиационный подвоз к удалённому хабу по-прежнему ищется через Яндекс. Полная поездка, даты подвоза и временная совместимость пока не проверены. Пустой ответ или ошибка Google Flights не удаляют схемы Яндекса. Ошибки и достижение лимита видны в предупреждениях источника «Наш алгоритм»; Google Flights не становится третьим самостоятельным планировщиком.

Переключение: `SEARCH_PLANNER_GOOGLE_FLIGHTS_ENABLED=false`. Бюджеты: `SEARCH_PLANNER_GOOGLE_FLIGHTS_MAX_REQUESTS` и `SEARCH_PLANNER_GOOGLE_FLIGHTS_MAX_OPTIONS`. В stage_local/dev флаг и бюджет запросов передаются route-builder из env. Обновление сохранённых результатов не запускается автоматически; новая версия используется при построении новых/ещё не обработанных заявок.

Ручной `search plan-route` при включённом Google Flights требует `-departure-from YYYY-MM-DD -departure-to YYYY-MM-DD -adults 2`. Эти параметры фиксируют только выборку дат для обнаружения схем. Поиск без дат возможен при выключенном Google Flights.

## Разнообразие схем и варианты подвоза

После получения цепочек результаты добавляются по кругу между парами аэропортов. `planner.max_candidates` ограничивает число схем; разные вокзалы прибытия поездом к одной авиационной цепочке не занимают отдельные места. `planner.max_rail_access_variants` ограничивает число вариантов подвоза внутри схемы (по умолчанию 5; диапазон 1–20, отсутствующее или нулевое значение использует 5 для совместимости старых YAML). Env: `SEARCH_PLANNER_MAX_RAIL_ACCESS_VARIANTS`.

Удержанные варианты хранятся в `rail_access_variants`: каждый содержит три исходных участка «переезд → поезд → переезд». `steps` сохраняет полный маршрут с первым вариантом для совместимости. Группы различают начальную железнодорожную станцию, авиационные цепочки, смены аэропортов и происхождение данных. Превышение каждого лимита отмечается отдельно; новые варианты подвоза к уже сохранённой схеме принимаются даже после заполнения лимита схем. Самостоятельный поиск дальних хабов и построение новых авиационных цепочек остаются будущими этапами.
