# 0002. Хранение данных и конфигурация сервисов

- Статус: принято, 2026-09-14.
- Область: единый подход для сервисов Travel Watch; реализация начата с Cabinet.

## Контекст

SQL находился в обработчиках авторизации. При появлении других сервисов нужен общий подход к запросам, который сохраняет явные транзакции и поддерживает будущие фильтры поиска. Настройки окружения и таймауты были распределены между переменными окружения и кодом.

## Решение

- Каждый сервис содержит собственный `internal/storage` и обращается только к своим данным. Единого пакета бизнес-запросов для всех сервисов нет.
- Строим запросы через goqu с PostgreSQL-диалектом и `Prepared(true)`. Выполняем их через `database/sql` с драйвером pgx, передавая параметры отдельно и используя `context`.
- Обработчики вызывают методы хранения без SQL и выражений goqu. Транзакционные операции объединяются в методы storage: регистрация с сессией и замена текущей сессии фиксируются целиком или откатываются целиком.
- Специфические выражения PostgreSQL допустимы внутри storage; пользовательские значения не вставляются в SQL-текст. Миграции остаются SQL-файлами Goose, автоматического изменения схемы через ORM нет.
- Каждый сервис хранит свой `config.yaml` в своей папке. Viper читает YAML и переопределения env в типизированную структуру; загрузка и проверка выполняются при старте. Секреты в Git не хранятся.
- Общие технические утилиты выносятся в `internal/platform` при появлении реального повторного использования, а не заранее.

## Последствия

Запросы и транзакции остаются явными, фильтры можно собирать программно. GORM и другие ORM параллельно не вводятся. goqu добавляет зависимость, но не управляет связями моделей и не скрывает границы транзакций.

Реализация Cabinet разделена на `internal/auth`, `internal/storage` и `internal/config`. Проверяются откат частичной регистрации и замены сессии, отмена запросов, приоритет конфигурации, неверные значения и переопределения env в Compose. Схема БД не меняется.

Загрузчик использует `AutomaticEnv`, `SetEnvKeyReplacer` и встроенную опцию Viper `ExperimentalBindStruct`: env для полей, отсутствующих в YAML, тоже учитываются при разборе структуры. Это поведение покрыто тестом; ручной перечень всех ключей не поддерживается.

## Изменение от 2026-09-23: goqu и SQL-текст

На практике запросы с блокировками и арендами (outbox, inbox, задания Search) писались SQL-текстом, а документация продолжала называть goqu единственным способом. Правило уточнено по фактическому применению:

- goqu — для запросов, которые собираются программно (необязательные фильтры, переменный набор полей или соединений), и для простых вставок и обновлений по ключу.
- SQL-текст — для статических запросов, построенных на выражениях PostgreSQL: `FOR UPDATE … SKIP LOCKED`, `ON CONFLICT … DO UPDATE … WHERE`, CTE с `UPDATE … FROM`, `CASE`, приведения типов, агрегаты JSONB. В goqu такие запросы в основном состоят из `goqu.L` и читаются хуже самого SQL; порядок `ORDER BY` по логическому выражению goqu не выражает вовсе.
- В обоих случаях значения передаются только параметрами; конкатенация и форматирование SQL из данных запрещены. SQL остаётся внутри `internal/storage`.

Формат SQL-текста (и фрагментов в `goqu.L`): строка в обратных кавычках, ключевые слова заглавными, без пробелов вокруг операторов и после запятых. Запрос до ~100 символов пишется одной строкой. В более длинном каждое из `FROM`, `JOIN`, `WHERE`, `GROUP BY`, `ORDER BY`, `ON CONFLICT`, `RETURNING` начинается с новой строки; `SET` остаётся при `UPDATE`, `VALUES` — при `INSERT`, `LIMIT` и `FOR UPDATE` — при `ORDER BY`. Строки продолжения начинаются с одного пробела; слишком длинное условие или список присваиваний переносится дальше по `AND`/`OR` и по присваиваниям. Тело CTE оформляется по тем же правилам между `WITH name AS (` и `)`. Применённые миграции не переформатируются.

Существующие запросы Cabinet и Search приведены к этому формату без изменения SQL.
