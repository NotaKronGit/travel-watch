# 0004. Передача созданной заявки через outbox

- Статус: принято, 2026-09-15. Контракт, атомарная запись в outbox и отправитель реализованы. Локальная Kafka добавлена в Compose; тест доставки с реальным брокером покрывает отказ, повтор и потерю подтверждения БД.
- Область: Cabinet → Kafka; потребитель Search будет отдельным этапом.

## Решение

Новую заявку и событие `travelwatch.events.v1.TripRequestCreated` сохраняем одной транзакцией в PostgreSQL Cabinet. Повтор CreateTrip с прежним request_id не создаёт нового события. Ранее созданные заявки автоматически не отправляем.

Контракт находится в `api/proto/travelwatch/events/v1/trip_request.proto`. Kafka value — бинарный Protobuf, key — UUID заявки. Поле schema_version равно 1. event_id обозначает событие, request_id — сохранённую заявку (не клиентский ключ идемпотентности). Топик по умолчанию `travelwatch.trip-requests.v1`, задаётся в YAML/env отправителя. Менять его при наличии backlog нужно как отдельную операцию миграции потока.

Событие содержит снимок географии на момент создания: внутренний ID города, источник и ID источника, русское название, страну, координаты, часовой пояс и необязательный IATA. Search не читает таблицы Cabinet. Сопоставление с транспортными пунктами остаётся задачей интеграции поставщиков; наличие IATA не подтверждает доступность перевозок. Email, сессия и другие персональные данные в событие не входят. Связь заявки с пользователем остаётся в Cabinet.

Отправитель работает отдельным процессом `cabinet publish-outbox` с ролью приложения. Один процесс обрабатывает по одной записи. Захват выполняется короткой транзакцией с `FOR UPDATE SKIP LOCKED`, ограниченным сроком аренды и новым токеном захвата. Сетевой запрос выполняется вне транзакции. Подтверждение и перенос повтора принимаются только для текущего токена; после падения процесса аренда истечёт и запись заберёт другой процесс.

Доставка at-least-once: после подтверждения Kafka процесс может упасть до отметки в БД, поэтому сообщение будет повторено с тем же event_id и байтами. Будущий Search обязан атомарно дедуплицировать event_id вместе с записью своих данных. Успешная отправка означает подтверждение Kafka, но не обработку Search.

Повторы используют экспоненциальную задержку с верхней границей. Число попыток не ограничено: события не удаляются и не переводятся в скрытый окончательный отказ. После исчерпания задержки выполняется следующая попытка. Ошибки видны через счётчик попыток, время следующей попытки и логи без payload. Автоматическая очистка outbox и эксплуатационные алерты — последующий этап.

Локальная Kafka — один узел KRaft в Compose, без публичного доступа. Это окружение разработки, не отказоустойчивый продакшен. Требования к TLS/SASL, репликации и сроку хранения Kafka определить до удалённого развёртывания. HTTP Cabinet не зависит от доступности Kafka.

Отмена и типизация сообщений в общем топике добавлены в [ADR 0005](0005-trip-lifecycle.md).
