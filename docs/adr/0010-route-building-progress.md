# ADR 0010: этап построения маршрутов и история заявки

Статус: принято для первого автоматического построения нашим планировщиком.

## Жизненный цикл и этап

Общий статус заявки (`saved`, `running`, `cancelled`, `completed`) отделён от этапа построения. Построение схем не означает расчёт цен или проверку расписаний. Считаются найденные схемы до отсечения по времени стыковок, в пределах покрытия и ограничений планировщика.

Этапы: `queued` → `building` → `awaiting_schedules`, `no_routes` или `failed`. Отмена окончательна. `awaiting_schedules` означает «Маршруты построены, ожидает проверки расписаний»; следующий обработчик пока отсутствует. Вся заявка остаётся `running`, а не `completed`. При ошибке или пустом результате она тоже остаётся активной, но с отдельным пояснением этапа.

## Выполнение и события

Search принимает создание через существующий inbox и в той же транзакции добавляет задание `route_building` и событие очереди в `progress_outbox`. Старые записи миграцией не запускаются. Позднее создание после отмены задания не создаёт.

Отдельный `build-routes` последовательно захватывает задания с `FOR UPDATE SKIP LOCKED`. Начало попытки и событие сохраняются атомарно. Вызовы Collector выполняются вне транзакции. Обработчик проверяет отмену и принадлежность аренды; таймаут построения меньше аренды. После аварии истёкшая аренда допускает новую попытку, максимум три по умолчанию. Исчерпание попыток становится записанной ошибкой. Обычная ошибка источника записывается без автоматического повторения всего поиска.

Результат JSON принадлежит Search. Завершение и событие фиксируются одной транзакцией, только для текущего токена неистёкшей аренды и неотменённой заявки. Ошибка поставщика без кандидатов отличается от успешной пустой выборки. Неполный результат с кандидатами допускает переход в ожидание следующего этапа с предупреждением.

`publish-progress` доставляет `TripRouteBuildingUpdated` в отдельный топик `travelwatch.route-building.v1`. Ключ — ID заявки, header `event_type` — полное имя Protobuf-сообщения. Повтор сохраняет event_id и payload; подтверждение в БД защищено токеном аренды. При ошибке публикации сообщение остаётся для повторной доставки после аренды. Гарантия at-least-once.

Cabinet командой `consume-progress` сохраняет событие в историю и обновляет проекцию одной транзакцией, затем подтверждает Kafka offset. История служит inbox: event_id и пара request_id/revision уникальны; повтор с другим payload — ошибка. Запоздавшее событие дополняет историю, но не откатывает текущий этап. Порядок задаёт возрастающая ревизия Search, а не часы сервера. Отменённая или завершённая заявка не возобновляется. Неизвестный контракт, конфликт идентичности или ошибка БД останавливают потребителя без подтверждения сообщения.

## История

Владельцу доступны время перехода, номер попытки, время начала и окончания, длительность, число схем и признак неполноты. Личные комментарии в события не передаются. Карточка и список опрашиваются раз в пять секунд; ошибка фонового запроса не стирает карточку и черновик комментария. Таймер активного построения приблизительный по часам браузера; окончательная длительность сохраняется Search. Время публикации/доставки Kafka не добавляется к длительности построения.

## Несколько планировщиков

Сейчас автоматически запускается только `graph`; идентификатор присутствует в событиях и истории. Gemini остаётся отдельным экспериментом и в ожидание текущего этапа не входит. Контракт потребителя пока принимает только настроенный для этого этапа `graph`.

При подключении Gemini следующим МР необходима отдельная запись результата каждого планировщика и зафиксированный при запуске набор участников попытки. Общий этап переключается только после завершения всех участников: результат, пустой ответ, ошибка или таймаут. Если есть схемы, переходить в ожидание расписаний с отметкой частичного результата при ошибках; если схем нет и все успешны — пустой результат; если схем нет и были ошибки — ошибка этапа. Изменение конфигурации не должно менять набор участников уже начатой попытки. Это правило согласовано; многопланировочное исполнение в текущий обработчик ещё не включено.

Сопоставление результатов — отдельный шаг Search после независимого построения. Совпадение схем у двух планировщиков не подтверждает перевозки и стыковки; уникальный вариант не считается автоматически ошибочным. Нужны нормализация физических узлов и режимов транспорта, сохранение происхождения и отдельная проверка транспортных связей.

## Границы

Нет автоматической проверки расписаний, цен, повторного ручного запуска, периодического обновления и API выдачи самих маршрутов. В истории выдаются этапы и счётчики, результаты хранятся в Search. Для локального этапа сохранён обмен с Collector через дочерний процесс; RabbitMQ не добавлен. Обработчик включается явно, чтобы обычный запуск стенда не расходовал квоты внешнего API.
