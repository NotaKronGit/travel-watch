# ADR 0012: чтение сохранённых схем через gRPC и mTLS

Статус: принято и реализовано для схем маршрутов.

## Решение

Search хранит отдельные результаты источников в своей PostgreSQL. События Kafka передают этапы, историю и счётчики, но не массивы схем. Cabinet не читает таблицы Search напрямую.

`RouteResultsService.GetRoutes` — внутренний gRPC/HTTP2 API процесса `search serve-results`. Cabinet сначала проверяет сессию и владение заявкой через собственный storage, затем вызывает Search. Клиент сгенерирован ConnectRPC и использует `WithGRPC`. Frontend обращается только к Cabinet через `TripService.GetTripRoutes`.

Чтение не запускает построение и не обращается к Яндексу или Gemini. API возвращает независимые страницы источников (до 10 схем на источник; интерфейс запрашивает 5). Чтение идёт внутри согласованного снимка транзакции. Для graph Search читает ограниченный набор (до 50 кандидатов, как в конфигурации планировщика), группирует железнодорожный подвоз и затем выбирает страницу. Для остальных источников PostgreSQL выбирает страницу из сохранённого JSON. Источники могут быть ещё в работе, завершиться ошибкой или вернуть неполную выборку. Ошибка чтения не означает пустой результат.

Таймаут Cabinet — 3 секунды, запроса БД Search — 2 секунды; максимальный ответ — 2 MiB. Контекст отменяется при уходе со страницы. В интерфейсе загрузка происходит при первом открытии, изменении истории прогресса, смене страницы или явном повторе. Переключение этапов сохраняет загруженные данные. Неизменные схемы не опрашиваются по таймеру.

## Идентичности сервисов

Обязателен TLS 1.3 с взаимной проверкой сертификатов. Search проверяет доверенный CA и DNS SAN клиента `cabinet`; Cabinet проверяет CA и имя сервера `search`. Сертификаты и ключи передаются в YAML/env как Base64 PEM. Base64 — формат передачи, а не шифрование. Значения исключены из JSON-представления конфигурации; секреты не коммитятся и не включаются в образы.

Для локальной разработки `make tls-init` выпускает отдельные env-файлы сервисов. Производственный выпуск, хранение в менеджере секретов и автоматическая ротация остаются отдельной эксплуатационной задачей. [Локальный запуск](../ops/route-results.md).

## Интерфейс и дальнейшие этапы

Нижняя стрелка состоит из секций «Заявка», «Схемы», «Стыковки». Нажатие переключает панель выше. Пройденные секции приглушены, но доступны; текущий этап и выбранная панель обозначаются отдельно. Комментарий и история остаются общими для заявки.

Схемы не удаляются при переходе к проверке расписаний. Продолжительность этапа не является TTL результата. Политику архивирования и срок хранения нужно определить отдельно. Проверка расписаний и цен пока не подключена: соответствующая панель показывает это явно. Контракты будущих предложений и истории цен не входят в этот ADR.

## Группировка железнодорожного подвоза

Новые результаты graph группируются при построении, до применения лимита схем. `steps` содержит представительный полный путь, `rail_access_variants` — все удержанные трёхшаговые префиксы подвоза, включая представительный. Отдельный лимит подвоза по умолчанию равен 5; усечение явно отмечается. Источники и физические коды станций сохраняются.

Ключ группы включает исходный город и код вокзала отправления, всю авиационную цепочку с кодами аэропортов и сменами аэропортов, конечный город и происхождение данных. Поддерживаются непрерывные схемы «переезд → поезд → переезд → один или несколько перелётов с возможными переездами → переезд». Неоднозначные коды, нарушенная непрерывность и другие формы не объединяются.

При чтении старые плоские результаты группируются до пагинации; новые вложенные варианты учитываются при формировании карточки. Карточка показывает общий подвоз, все последующие участки и число удержанных вариантов. Представление не изменяет JSON в БД. Конкретные вокзалы и расписания выбираются на этапе стыковок.

`SourceRoutes.total`, страницы и `has_more` относятся к отображаемым схемам. Для новых построений события также считают схемы; исторические события не переписываются и могут содержать прежнее число плоских кандидатов. Сопоставление graph и Gemini остаётся отдельным этапом.

Изменение JSON добавочное, миграция БД не требуется. Старый reader сможет прочитать `steps`, но не покажет дополнительные варианты из `rail_access_variants`; для корректного отображения обновляются и builder, и Search results API. Существующие заявки не пересчитываются автоматически.
