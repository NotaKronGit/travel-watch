# 0005. Отмена заявки и личный комментарий

Статус: принято, 2026-09-15.

## Решение

Удаление заявки означает окончательную отмену с сохранением записи и доступа владельца к её истории. Физического удаления и отдельного флага active нет: активными считаются `saved` и `running`, неактивными — `cancelled` и `completed`.

- `saved` — сохранена, Search ещё не подтвердил начало обработки.
- `running` — выполняется; значение подготовлено для будущей интеграции Search.
- `cancelled` — отменена владельцем, повторно активировать этот ID нельзя.
- `completed` — завершена; значение подготовлено для Search. Условие завершения постоянного отслеживания пока не определено.

Сейчас создание выставляет `saved`, CancelTrip переводит `saved`/`running` в `cancelled`. Повтор отмены возвращает успех без нового события и изменения cancelled_at; отмена completed отклоняется. Клиент не может произвольно назначить статус. Отправка в Kafka не переводит заявку в running. Повтор CreateTrip по прежнему ключу не возобновляет отменённую заявку. Для новой попытки пользователь создаёт новую заявку с новым ключом.

Изменение статуса и событие `TripRequestCancelled` сохраняются одной транзакцией. Строка заявки блокируется с проверкой владельца. Уникальность `(request_id,event_type)` гарантирует единственное событие отмены; повторная доставка через outbox сохраняет его event_id и payload.

## Изменение от 2026-09-23: истечение заявки

Добавлен статус `expired` (неактивный, окончательный) и `expired_at`. Заявка истекает, когда её последний день выезда (`departure_to`) закончился в часовом поясе города отправления; часовой пояс, неизвестный PostgreSQL, сравнивается по UTC, чтобы ни одна заявка не осталась активной навсегда. Проверку выполняет процесс `serve` по таймеру (`trips.expiry_interval`, по умолчанию 10 минут, первый проход при старте; пачка `trips.expiry_batch`). Каждая заявка переводится в собственной транзакции: блокировка строки, повторная проверка статуса `saved`/`running`, обновление и событие `TripRequestExpired` в outbox. Поэтому несколько экземпляров `serve` не создают повторных событий.

Истёкшую заявку нельзя отменить (как `completed`); отмена и истечение взаимоисключающие. Прогресс Search не возобновляет истёкшую заявку. В отличие от отмены, Search по `TripRequestExpired` только прекращает работу: уже сохранённые схемы и проверки расписаний остаются доступны для чтения, этап построения не переводится в «отменено». `completed` по-прежнему зарезервирован. Событие предназначено и для будущего уведомления в Notification.

При выкатке Search обновляется раньше Cabinet: старая версия Search не принимает неизвестный тип события. Откат миграций при наличии истёкших заявок или их событий завершается ошибкой, как и для отмены.

## Контракт событий

Создание и отмена передаются в одном топике с ключом UUID заявки. Kafka header `event_type` содержит полное Protobuf-имя: `travelwatch.events.v1.TripRequestCreated` или `travelwatch.events.v1.TripRequestCancelled`. Для исторических сообщений без header допустим только прежний формат создания: до этого изменения других типов не существовало. Неизвестные значения header нельзя декодировать как создание.

Доставка остаётся at-least-once. При нескольких отправителях или повторах отмена может прийти раньше создания. Search обязан запомнить отмену даже для ещё неизвестного ID, дедуплицировать event_id и не возобновлять обработку после позднего создания или результата. Приём создания и отмены реализован по [ADR 0006](0006-search-inbox.md); обработка результатов ещё не реализована.

## Комментарий и история

Комментарий — одна личная редактируемая заметка владельца до 2000 Unicode-символов, доступная в карточке после создания. Пустая строка очищает заметку. Текст отображается как обычный текст и не передаётся в события Search. Редактирование разрешено в любом статусе и не меняет статус. При одновременных изменениях из нескольких вкладок сохраняется последняя успешная запись; отдельного журнала заметок и переписки нет.

Все заявки, включая отменённые, остаются в списке и доступны по прямой ссылке владельцу. История здесь — список заявок с текущими статусами и временем отмены, а не журнал каждого перехода.

## Обновление

Миграция 00009 присваивает существующим заявкам saved и пустой комментарий, не создавая событий. Перед обновлением остановить старые процессы serve и publish-outbox, затем применить миграцию и запустить новую версию обоих: старый отправитель не умеет добавлять тип сообщения. Для stage_local выполнить `make stage-local-stop`, затем `make stage-local-up`.

Откат миграции не удаляет события отмены автоматически: при их наличии восстановление старого CHECK завершается ошибкой и транзакция откатывается. Нужен отдельный план обращения с уже доставленными отменами; их нельзя терять ради отката. Даже при отсутствии таких событий откат удаляет статусы, комментарии и cancelled_at. Откат приложения после использования отмены также требует отдельного решения.
