# Архитектура Travel Watch

Статус: общая архитектура остаётся ориентиром. Реализованы авторизация, справочник городов и создание, список и просмотр заявок в Cabinet и frontend; Search, Collector, Notification и брокеры пока не реализованы.

## Сервисы и владение данными

Monorepo с одним `go.mod` на старте, отдельными бинарниками и Dockerfile для сервисов.

| Сервис | Ответственность |
| --- | --- |
| [Cabinet](services/cabinet.md) | Пользователи, сессии, заявки и пользовательский API |
| [Search](services/search.md) | Расписание проверок, дедупликация поисков, предложения и история, составление маршрутов, проверка условий уведомления |
| [Collector](services/collector.md) | Адаптеры поставщиков, выполнение заданий и нормализация данных |
| [Notification](services/notification.md) | Telegram-бот, привязки пользователей, уведомления и доставка |

Каждый сервис владеет своими данными. Локально предполагается один PostgreSQL с отдельными базами и ролями; сервисы не читают чужие таблицы. Планировщик и обработчики Search могут работать как отдельные процессы одного сервиса.

## Поток данных

1. Cabinet сохраняет заявку и публикует её изменение в Kafka.
2. Search обрабатывает изменение, объединяет одинаковые поиски и планирует проверки.
3. Search выдаёт задания на запросы к источникам через RabbitMQ.
4. Collector выполняет задания ограниченными пулами воркеров и публикует наблюдения в Kafka.
5. Search обрабатывает наблюдения, строит маршруты, сохраняет результаты и генерирует события уведомлений.
6. Notification доставляет уведомления в Telegram. Веб-кабинет получает результаты через пользовательский API; контракт получения данных из Search ещё предстоит определить.

RabbitMQ используется для поручений выполнить запрос к источнику, Kafka — для фактов и результатов, доступных независимым обработчикам и повторной обработке. Периодичность обеспечивает планировщик Search.

Необходимо предусмотреть outbox, идемпотентность обработчиков, повторные доставки, backoff, ограниченные ретраи и частичные результаты проверок. Доставка Telegram не имеет гарантии exactly-once.

## Предлагаемый стек

| Область | Технологии и назначение |
| --- | --- |
| Backend | Go, ограниченные worker pools, `context`, таймауты, graceful shutdown |
| Хранение | PostgreSQL |
| Доступ к БД | goqu + database/sql с pgx; SQL-миграции Goose |
| Обмен сообщениями | Kafka для событий, RabbitMQ для заданий |
| Общие лимиты | Redis для лимитов поставщиков между воркерами; кеш поиска необязателен |
| Frontend | React, TypeScript, React Admin, Material UI, Vite |
| API | ConnectRPC и Protobuf |
| Локальное окружение | Docker Compose |
| CI/CD | GitHub Actions, образы в GHCR с тегами commit SHA и dev-latest |

## Структура репозитория

Созданы общий `go.mod`, исходники и миграции Cabinet, Protobuf-контракт и сгенерированные Go/TypeScript-типы, frontend и Compose для PostgreSQL. Пустые каталоги будущих компонентов содержат `.gitkeep`. Добавлены Dockerfile Cabinet/frontend, stage_local в Compose и GitHub Actions для проверок и сборки образов; удалённый деплой не настроен.

```text
services/
  cabinet/{cmd,internal,migrations}/
  search/{cmd,internal,migrations}/
  collector/{cmd,internal,migrations}/
  notification/{cmd,internal,migrations}/
frontend/
api/proto/
gen/
internal/platform/
deploy/compose/
docs/
  product.md
  architecture.md
  roadmap.md
  services/
  adr/
.github/workflows/
```

`internal/platform` предназначен только для общего технического кода. Бизнес-логика сервиса остаётся внутри него и не импортируется другими сервисами. Существенные архитектурные решения будут фиксироваться в `docs/adr`.

Единый подход к хранению и конфигурации принят в [ADR 0002](adr/0002-service-storage-and-configuration.md): собственный `internal/storage` каждого сервиса, запросы через goqu, явные транзакции и отдельный YAML-конфиг с переопределениями env. В Cabinet этот подход реализован; остальные сервисы ещё не созданы.

## Масштабирование

По мере необходимости можно добавлять реплики API, воркеры Collector с общими лимитами поставщиков, обработчики Search и отправители уведомлений. Kafka partitions и consumer groups распределяют обработку событий. Для планировщика нужно исключить дублирование проверок между экземплярами; для истории — определить хранение и индексы. Конкретные механизмы выбираются при реализации.

Этапы реализации, CI/CD и открытые вопросы находятся в [плане разработки](roadmap.md). Пользовательские сценарии и правила корректности — в [описании продукта](product.md).

Импорт географического справочника Cabinet через интерфейс источника описан в [ADR 0003](adr/0003-city-catalog-source.md). Реализованы GeoNames-адаптер, тестовый источник и отдельная команда импорта; API подсказок подключён к форме создания заявки.
