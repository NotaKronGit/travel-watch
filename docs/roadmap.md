# План разработки

Статус: подготовлены документация и каталоги monorepo. Код, Go-модуль и локальное окружение ещё не созданы; этапы ниже не завершены.

## Последовательность

1. Описать первый сквозной сценарий: поля заявки, состояния, контракты заданий и событий, получение результатов кабинетом.
2. Подготовить каркас monorepo и минимальное локальное окружение.
3. Реализовать сценарий на тестовом источнике: создание заявки → Search → RabbitMQ → Collector → Kafka → Search → результат в вебе → Telegram.
4. Добавить периодические проверки, историю, условия уведомления, паузу и возобновление; проверить поведение при сбоях и повторных доставках.
5. Подключать реальные источники после проверки доступности API, ограничений и условий использования.

Работа ведётся небольшими шагами с объяснением решений: проект служит в том числе для изучения Go, распределённых систем и незнакомого пользователю React/TypeScript.

## Проверки и развёртывание

План CI: форматирование и линт, Go-тесты и race detector, проверка типов/тесты/сборка frontend, проверка контрактов, интеграционные сценарии и сборка Docker-образов. На старте проверяется весь проект; выбор проверок по изменённым сервисам возможен позже с учётом зависимостей.

Для будущего CD: образы с commit SHA, обратно совместимые миграции и health checks. Общий pipeline должен допускать независимый деплой сервисов. Сначала Docker Compose; отдельные ресурсы для БД и брокеров и Kubernetes — по необходимости.

Команд запуска и тестирования пока нет. Их следует добавлять вместе с проверенной реализацией. Публикация и развёртывание ещё не запрошены.

## Открытые вопросы

- Источники авиа- и железнодорожных данных: API, покрытие, лимиты, стоимость и условия использования.
- Точные границы первого маршрута и правила допустимой стыковки.
- Ключ одинакового поиска и разделение общих параметров поиска и пользовательских условий уведомления.
- Модель тарифов, валют и сравнения цен, включая базу для расчёта снижения.
- Контракты между сервисами, состояния проверки и правила обработки частичных результатов.
- Частота проверок, хранение истории и правила подавления повторных уведомлений.
