# План разработки

Статус: подготовлены документация, структура monorepo и первый локальный сценарий Cabinet: регистрация, вход, сессии и кабинет React Admin. Добавлены PostgreSQL в Compose, миграции и проверки, полный stage_local и workflow GitHub Actions. Search принимает события заявок; поиск предложений и другие сервисы ещё не реализованы.

## Последовательность

1. Первая форма, API подсказок, сохранение, список, просмотр, отмена своих заявок и личный комментарий реализованы по [спецификации заявки](specs/trip-request.md): поездка в одну сторону, города, диапазон дат отправления и взрослые пассажиры. Согласован мировой охват подсказок с автоматическим наполнением справочника; импорт GeoNames реализован отдельной командой с тестовым источником без внешних запросов в CI. Завершить описание состояний заявки, контрактов заданий и событий и получения результатов кабинетом.
2. Каркас monorepo, PostgreSQL и базовая авторизация Cabinet готовы; расширять локальное окружение по мере реализации остальных компонентов.
3. Реализовать сценарий на тестовом источнике: создание заявки → Search → RabbitMQ → Collector → Kafka → Search → результат в вебе → Telegram.
4. Добавить периодические проверки, историю, условия уведомления, паузу и возобновление; проверить поведение при сбоях и повторных доставках.
5. Подключать реальные источники после проверки доступности API, ограничений и условий использования.

Работа ведётся небольшими шагами с объяснением решений: проект служит в том числе для изучения Go, распределённых систем и незнакомого пользователю React/TypeScript.

## Текущий этап: Cabinet → Kafka → Search

Контракт `TripRequestCreated` и сохранение новой заявки вместе с событием в outbox реализованы по [ADR 0004](adr/0004-trip-request-outbox.md). Старые заявки не дополняются событиями. Отдельный отправитель с подтверждением Kafka, арендой записей и повторами реализован. Локальная Kafka в Compose и проверки доставки при сбоях с реальным брокером реализованы. Потребитель Search реализован: собственная БД, транзакционный inbox, подтверждение Kafka после записи и окончательная отмена при любом порядке доставки ([ADR 0006](adr/0006-search-inbox.md)). Реализованы модель транспортных узлов и построение кандидатов на фиксированных тестовых данных по [описанию алгоритма](specs/route-building.md), пока без подключения к потребителю. Сборка предложений и проверка стыковок также реализованы на [синтетических расписаниях](specs/scheduled-journeys.md); планирование проверок и задания Collector через RabbitMQ добавляются после определения входов и выходов алгоритма.

## Получение результатов: Cabinet → Search по gRPC с mTLS

Реализовано чтение сохранённых схем источников через gRPC/HTTP2 с mTLS, проверкой владельца в Cabinet и пагинацией. На карточке добавлены переключаемые панели этапов. [ADR 0012](adr/0012-saved-routes-grpc.md), [запуск](ops/route-results.md).

Далее: контракты конкретных предложений и истории цен, политика хранения результатов, производственный выпуск и автоматическая ротация сертификатов. Проверка расписаний остаётся отдельным этапом.

## Позже: синхронизация справочника по таймеру и проверка полноты переводов

Запланировано одним этапом; сейчас [импорт GeoNames](ops/city-catalog.md) запускается только вручную. Таймер и дополнительная защита пока не реализованы.

- Добавить периодический запуск существующего импортёра. Интервал и включение задавать через YAML/env; конкретный механизм расписания определить при реализации. Сохранить ручной запуск и исключить одновременные обновления.
- До включения таймера исправить замечание P2: сейчас минимум городов проверяется до фильтрации по русскому имени, а после неё достаточно одной записи. Корректная по формату, но неполная выгрузка переводов может привести к успешной публикации маленького набора и массовой деактивации ранее сохранённых городов.
- Проверять полноту локализованного набора после фильтрации и до записи в БД: добавить отдельный настраиваемый минимум городов с русским именем. Значение порога определить при реализации; дополнительно рассмотреть ограничение резкого сокращения относительно предыдущего успешного импорта.
- При отклонении снимка сохранять предыдущий справочник и его метаданные без изменений. Предусмотреть видимый статус ошибки и время последнего успешного обновления.
- Добавить тесты на полный исходный список с одним русским названием, срабатывание и границы порога, сохранение предыдущего набора при отказе и успешное обновление полноценным снимком. Тесты и CI продолжают использовать фиксированные данные без скачивания GeoNames.

## Позже: резервный источник географического справочника

Отложено до обновления по таймеру и проверки полноты данных. Сейчас при ошибке импорта сохраняется последний успешный справочник в БД; автоматическое переключение между источниками не реализовано.

- Выбрать резервный источник стран, регионов и городов, проверить покрытие, локализацию, лицензию и ограничения. Добавить адаптер через существующий интерфейс `catalog.Source`.
- Определить сопоставление идентификаторов между источниками с сохранением внутренних UUID и связей с заявками. Различия названий и покрытия не должны создавать дубли или массово деактивировать города.
- Определить условия переключения и возврата к основному источнику, приоритет данных и правила разрешения расхождений. Настройки задавать через YAML/env; происхождение и версию данных сохранять явно.
- Публиковать резервный снимок только после проверки полноты и корректности. Если ни один источник не дал подходящих данных, сохранять последний успешный справочник и показывать ошибку обновления.
- Проверить недоступность источников, неполные снимки, конфликтующие записи, повторное переключение и сохранение ссылок из заявок. Тесты и CI используют фиксированные данные без внешних загрузок.

## Позже: Telegram-уведомление о входе с нового IP

Запланировано после реализации Notification и привязки Telegram к аккаунту; пока не реализовано.

- Уведомлять привязанный Telegram об успешном входе с ранее неизвестного IP. Изменение IP при смене сети или использовании VPN само по себе не означает взлом аккаунта.
- Cabinet определяет новый адрес и сохраняет событие вместе с успешным созданием сессии через outbox. Notification получает событие через Kafka и отвечает за доставку, повторы и защиту от дублирования. Сбой Telegram не должен мешать входу.
- Определить, что считать новым IP, как долго помнить адреса, как получать адрес за доверенным proxy и подавлять повторные уведомления. Также определить состав сообщения, настройки пользователя и срок хранения данных о входах.
- Проверить повторную доставку события, недоступность Telegram и отсутствие привязки. Не добавлять таблицы и интеграцию заранее, до реализации этого этапа.

TOTP отложен до завершения базового сценария регистрации, входа и серверных сессий. Вернуться к этому этапу перед публичным запуском.

- Добавить возможность включить TOTP в настройках аккаунта с подтверждением подключения.
- Предусмотреть защиту секрета, резервные одноразовые коды, восстановление доступа и безопасное отключение второго фактора.
- Если появится панель администратора с доступом к чужим данным, сделать MFA обязательной до открытия такого доступа.
- Изменения БД добавить отдельной миграцией при реализации; заранее поля TOTP не создавать.

## Проверки и развёртывание

Подготовлен CI в GitHub Actions: форматирование, Buf lint, go vet, Go-тесты с race detector, типы/тесты/сборка frontend, воспроизводимость генерации контрактов, интеграционные и браузерные сценарии, сборка Docker-образов. Workflow начнёт выполняться после публикации ветки и открытия PR. На старте проверяется весь проект; выбор проверок по изменённым сервисам возможен позже с учётом зависимостей.

После успешных проверок push в main workflow публикует образы с commit SHA в GHCR. Локальное развёртывание выполняется через `make stage-local-up`: сборка, миграции, запуск и health checks. Удалённый CD отложен. Для будущих миграций сохранять обратную совместимость. Общий pipeline должен допускать независимый деплой сервисов. Сначала Docker Compose; отдельные ресурсы для БД и брокеров и Kubernetes — по необходимости.

Добавлен режим `make dev-up` для скачивания готовых образов без сборки; после публикации всех трёх образов CI обновляет `dev-latest`. Настройки и команды — в [инструкции dev](ops/dev-images.md).

Команды локального запуска и проверок описаны в [инструкции разработки](ops/local-development.md). Публикация образов в GHCR и удалённое развёртывание ещё не выполнялись.

До публичного запуска: подтверждение email, восстановление пароля, MFA, HTTPS и настройка защиты входа с учётом proxy/реплик.

## После кандидатов: показатели собранного маршрута

Подготовлена сборка поездок на синтетических расписаниях с началом и концом поездки. Сводные показатели стоимости, ожидания и пересадок и их отображение пока отложены.

- Показывать стоимость и её полноту: неизвестные цены участков не считать нулевыми; отдельно определить сравнение валют и тарифов.
- Рассчитывать общую длительность от начала до конца поездки, включая транспорт, наземные переезды и ожидание. Границы начального и конечного городского участка определить явно.
- Показывать суммарное время ожидания и ожидание каждой стыковки. Переезд между узлами не учитывать повторно как ожидание; отдельно согласовать учёт регистрации, контроля и запаса на задержки.
- Показывать общее количество пересадок между основными транспортными участками и отдельно количество пересадок с физическим переездом в другой узел (вокзал → аэропорт, аэропорт → другой аэропорт и т. п.). Начальный и конечный трансферы учитывать отдельно от пересадок.
- Для примера поезд → переезд вокзал–аэропорт → самолёт: одна пересадка между основными участками, из неё одна с переездом. Для двух перелётов из одного аэропорта: одна пересадка без межузлового переезда; кандидаты авиапересадок и проверка временной совместимости поддерживаются, сводные показатели ещё не реализованы.
- При неизвестном времени участка помечать показатели как неполные. Вычислять длительности по абсолютному времени с учётом местных часовых поясов.
- Проверить ночные стыковки, смену часовых поясов, отсутствие переезда, смену аэропорта, неизвестные значения и отсутствие двойного учёта времени. Сравнение «дешевле / быстрее / меньше пересадок» добавить на основе этих показателей.


## Эксперимент с LLM для кандидатов маршрута

Интерфейс Planner, общий валидатор и сравнение двух алгоритмов реализованы по [ADR 0007](adr/0007-route-planners.md). Добавлен Gemini Planner и `make search-compare` для пяти синтетических направлений; HTTP-контракт проверяется без внешнего API. После двух частично успешных прогонов выполнен полный прогон Gemini 3.5 Flash-Lite: все 5 кейсов и 9 кандидатов совпали с GraphPlanner. Добавлена безопасная диагностика API; причина прежних 403 и таймаутов не установлена, стабильность ещё требует оценки.

- Реализовано: Gemini API, модель и ограничения через YAML/env, последовательные запросы без повторов, отчёт по токенам. Тариф аккаунта проверяется у провайдера.
- Добавить выбор алгоритма и режим сравнения через YAML/env при подключении построения кандидатов к Search.
- Сравнить GraphPlanner и LLM на одинаковых транспортных данных: общие/пропущенные/дополнительные валидные кандидаты, ошибки, время и стоимость. Отдельно проверить недопустимые связи и неполное покрытие.
- Не доверять LLM расчёт расписаний, времени, цены и доступности. Новые предложенные связи подтверждать источником до включения в маршрут.

## Следующий этап: реальные транспортные источники

[Исследование источников](research/transport-sources.md) рекомендует начать с собственного каталога аэропортов Search на OurAirports и ручного импорта. Актуальные авианаправления, связь аэропортов с городами, часовые пояса и источники наземных переездов требуют отдельного решения. Каталог аэропортов не подтверждает наличие рейсов.

### Периодическая синхронизация городов и аэропортов

Добавить запуск по расписанию для обоих справочников поверх ручных команд. Период и механизм запуска определить при реализации. Предусмотреть таймауты, ограниченные повторы, защиту от пересечения запусков, проверку полноты до публикации, сохранение последнего успешного снимка и видимость ошибок/возраста данных. Для городов включить ранее отложенную защиту от неполной русской локализации; для аэропортов сохранить проверки абсолютного минимума и резкого сокращения. Автоматический запуск при старте приложения и внешние загрузки в CI не добавлять.

### Железнодорожные станции

Для ЖД принят поиск станций онлайн через подключаемых провайдеров Collector, без предварительного импорта мирового каталога. Найденные станции планируется сохранять с устойчивыми ID и кодами источников; обновление и кэширование — по условиям поставщиков. В Collector реализованы отдельные интерфейсы поиска станций/поездов и синтетический провайдер. Следующий этап — выбор реального API и проверка покрытия; затем адаптер и межсервисные контракты. Разные вокзалы города не объединять: наземные переезды относятся к конкретным станциям.

## Экспериментальные отчёты в кабинете

Согласовано независимое построение нашим алгоритмом и Gemini: только направление и общие условия, без передачи графа и маршрутов конкурентов. Gemini самостоятельно предлагает схемы; веб-поиск и подтверждение перевозок ещё не подключены. Ручной самостоятельный планировщик описан ниже; его подключение к отчёту в кабинете остаётся отдельным шагом. Rome2Rio исключён по решению пользователя. [Методика](research/planner-comparison/README.md).

Прежние результаты на общем графе Rome2Rio сняты с независимого сравнения. Проверено [покрытие Яндекс Расписаний](research/yandex-coverage.md): авиа- и железнодорожные данные есть, наземный участок Бангкок → Паттайя источник не закрыл. Адаптер отдельных связей и самостоятельный выбор узлов добавлены в ручной команде; инструменты Gemini ещё предстоят. Неподтверждённые варианты показываются с предупреждениями, но невозможные временные стыковки не разрешаются. Для автоматических результатов заявки нужны хранение Search и согласованный API Cabinet → Search.

### Самостоятельный планировщик на реальных связях

Реализован отдельный ручной `make search-plan-route`: географический выбор узлов из OurAirports, проверка связей и исследование прилётов через Collector/Яндекс, варианты поезд + перелёт и местный + международный перелёт. Предполагаемые переезды отмечаются предупреждениями. [Инструкция и ограничения](ops/route-planner.md). Это ограниченный перебор без проверки дат; к отчёту в кабинете и событиям заявок он пока не подключён.

Далее: оценить пропуски ограниченной выборки на нескольких направлениях, подключить результат к сравнению, дать Gemini собственные инструменты получения связей; затем расписания и проверка стыковок. Сохранение и автоматический расчёт заявок — отдельный этап.

### Этапы построения и история заявки

Добавлены очередь для новых заявок, отдельный обработчик нашего планировщика, сохранение результатов Search, события прогресса и история Cabinet с таймерами и количеством схем до проверки временной совместимости. Успешное построение переводит этап в ожидание проверки расписаний, а не завершает заявку. [ADR 0010](adr/0010-route-building-progress.md).

Реализован автоматический независимый Gemini: набор участников сохраняется при первом захвате задания, источники работают параллельно и сохраняют отдельные результаты. Общий этап ждёт всех, а после аварии повторяются только незавершённые источники. [ADR 0011](adr/0011-independent-planner-runs.md).

Отдельно добавить сопоставление схем после нормализации физических узлов и видов транспорта. Хранить происхождение и отмечать «Совпадает у нескольких планировщиков» / «Найден одним». Подтверждение транспортными данными отделять от совпадения; уникальность не считать ошибкой, совпадение — гарантией доступности. После этого проверять расписания и время стыковок и показывать число прошедших/отсеянных схем.

Добавить управляемый повтор построения после ошибки и периодические проверки. История и inbox не очищаются для перезапуска.

### Скорость построения и инструменты Gemini

- Измерить время отдельных операций Яндекса, количество повторных запросов и долю полезных ответов. На основе замеров сократить лишние запросы и проверить кеширование в рамках условий поставщика.
- Независимые запросы к Яндексу выполнять с ограниченным параллелизмом. Учесть квоты, HTTP 429, таймауты, отмену и общий бюджет запроса; не создавать неограниченное число горутин. При нескольких экземплярах согласовать общий лимит нагрузки на провайдера.
- Добавить Gemini инструменты поиска транспортных узлов и связей через Collector. Модель самостоятельно выбирает вызовы и промежуточные узлы; результаты нашего планировщика ей не передаются. Ограничить количество вызовов инструментов, токены и длительность. Предложения модели отделять от связей, подтверждённых источником.
- Параллельный запуск graph и Gemini с сохранённым набором участников, историей каждого и ожиданием всех реализован. При добавлении следующих источников сохранить эти гарантии и ограничение конкурентности.
- Разделить лимиты конкурентности между заявками, между планировщиками одной заявки и внутри провайдера. Несколько планировщиков, использующих Яндекс, не должны независимо исчерпывать одну общую квоту.
- Сравнить последовательный и параллельный режимы на одинаковых направлениях: длительность, число запросов, ошибки, полнота и состав кандидатов. Ускорение не должно терять результаты или менять смысл статусов.

## Представление и отбор схем поездки

Реализована группировка вариантов железнодорожного подвоза к одному аэропорту при чтении graph, до пагинации, с сохранением всех исходных вариантов для проверки стыковок ([правила](adr/0012-saved-routes-grpc.md#группировка-железнодорожного-подвоза)).

Далее: сопоставлять структурированные схемы независимых источников, сохранять происхождение каждого совпадения. Совпадение не считать подтверждением доступности. После получения расписаний и цен выбирать 3–5 полезных вариантов: удобный, быстрый, дешёвый на всех пассажиров с багажом и трансферами, компромиссный. Один маршрут может соответствовать нескольким критериям; остальные сохранять в «Других вариантах». До этих данных не называть схемы самыми быстрыми или дешёвыми и не отбрасывать дополнительные пересадки только по числу участков.

## Дополнительный авиационный источник

Реализованы ручной эксперимент и подключение Google Flights/Fli к построению схем нашего планировщика через Collector ([результаты и правила](ops/flight-search.md)). На SVO → BKK получена неполная пустая выдача, поэтому Яндекс сохраняется. Для обнаружения схем согласованы до трёх дат: начало, середина и конец диапазона заявки. На этапе расписаний ещё предстоят разрешение timezone аэропортов, нормализация предложений и проверка временной совместимости. GraphPlanner и LLM должны сами выбирать аэропорты для запросов; общий провайдер не означает независимое подтверждение из двух источников. Из новых авиационных источников на текущем этапе продолжаем только с Google Flights/Fli; Яндекс остаётся подключённым. AirTreks отложен.


## Позже: повторная оценка AirTreks

Сейчас не подключаем к планировщикам. Вернуться при появлении задачи сложной авиационной поездки: несколько посещаемых городов, сочетания перевозчиков и правила сборки билетов. Это не замена мультимодальному поиску поездов, перелётов и наземных переездов.

В ручной проверке 16 сентября 2026 `hub_check` не дал конкретных данных для DME → SSH, SVO → BKK и DME → BKK; для IST → BKK предложил Доху. `plan_route` для DME → SSH не определил перевозчика и рекомендовал консультанта. Городской код MOW сервис преобразовал в SVO, не выполнив поиск по всем аэропортам Москвы. Запросы прошли успешно, но польза для наших направлений оказалась ограниченной; это не вывод об отсутствии рейсов или о всём покрытии сервиса.

Перед возможным подключением проверить соответствие новой задаче, покрытие, происхождение рекомендаций и актуальные условия API. `isDead=false` и высокий `confidence` не считать подтверждением доступности рейса или допустимости стыковки. [Описание AirTreks](https://airtreks.com/developers).

## Оптимизация бюджета и дальнейшее расширение перебора схем

После подключения Google Flights улучшить именно наш алгоритм:

- Реализованы приоритет крупных аэропортов до обрезки, чередование хабов по municipality и проходы Google Flights по разным парам прежде повторных дат. Расширение на дальние узлы вне текущего радиуса и более точное определение агломераций остаются следующими шагами.
- Реализованы отдельные лимиты схем и вариантов железнодорожного подвоза. Вокзалы сохраняются внутри схемы и не занимают её общий лимит; чтение поддерживает старые результаты и цепочки с несколькими перелётами.
- Добавить собственный перебор авиационных цепочек с пересадками. Сейчас используются заданные типы схем Яндекса и готовые авиационные цепочки, возвращённые Google Flights; это не полный поиск по транспортному графу.

Сохранить независимость GraphPlanner/Gemini, явную неполноту и исходные транспортные варианты для следующего этапа стыковок.

## Обязательно: сокращение внешних запросов

Отдельная обязательная задача после текущего улучшения перебора. Более разнообразная выдача ещё не означает меньших затрат: сравнение сложных направлений показало рост общего числа обращений. [Замеры](research/complex-routes-optimization/README.md).

- Измерить фактические обращения к Яндексу и Google Flights отдельно по операциям, повторным параметрам, времени и доле полезных ответов. Учитывать весь поиск, включая станции и железнодорожный подвоз, а не только авиационные пары.
- Убрать повторные обращения внутри одного построения и лишнее раскрытие вокзалов и связей; переиспользовать уже полученные данные в рамках расчёта. Сохранить конкретные станции и полезные варианты подвоза для дальнейшей проверки стыковок.
- Согласовать бюджеты вызовов и критерии остановки. Исчерпание бюджета и ошибки источника обозначать как неполноту, а не отсутствие маршрутов.
- Проверить до/после на одинаковых параметрах Курск → Лос-Анджелес, Воркута → Рейкьявик и Йошкар-Ола → Сидней: число внешних запросов, длительность, ошибки и состав найденных схем. Сокращение вызовов не должно достигаться незаметной потерей полезных маршрутов.

Эта задача не требует внедрения Redis: общий кеш ответов поставщиков отложен отдельно.

## Далее: актуальность результатов одной заявки

Планируется после улучшения перебора схем, отдельным МР. Сохранение схем в PostgreSQL уже реализовано; срок актуальности, автоматическое обновление и описанные ниже состояния ещё предстоит добавить.

- Хранить последний результат и время его проверки в PostgreSQL Search. Открытие заявки в пределах срока актуальности читает сохранённые данные и не запускает повторные обращения к источникам. Redis для этого сценария не требуется.
- Задать настраиваемый срок актуальности и время следующей проверки. Конкретный срок определить при реализации с учётом типа данных и ограничений поставщиков; 30 минут из обсуждения — пример, не принятое значение по умолчанию. Срок актуальности не гарантирует, что данные у поставщика не изменились раньше.
- После истечения срока помечать результат как устаревший. Для активного отслеживания запускать фоновую проверку по расписанию; открытие страницы не должно создавать дубли заданий. Во время обновления сохранять предыдущие результаты на экране с временем наблюдения и статусом «Данные устарели, обновляем». Пауза и отмена отключают автоматические проверки.
- По завершении показывать новый результат и его время проверки. Не смешивать результаты разных параметров заявки; не позволять позднему ответу старой проверки перезаписать более новый результат. Предусмотреть историю наблюдений; срок хранения истории определить отдельно.
- Различать успешную проверку без прежнего варианта («Не найден при последней проверке»), ошибку источника и неполную проверку («Не удалось подтвердить актуальность»). Сбой или усечение поиска не означают исчезновения маршрута; не стирать прежние варианты как недоступные и не обновлять время их успешной проверки из-за неудачной попытки.
- Проверить отсутствие повторных обращений при просмотре свежего результата, истечение срока, сохранение предыдущего результата во время обновления, ошибки и частичную выдачу, защиту от параллельных дублей и запоздавших ответов.

## Отложено: временный кеш Collector в Redis

По текущему решению сохранённых схем в PostgreSQL достаточно; Redis и дополнительный кеш сейчас не внедряем. Просмотр сохранённого результата не требует повторного построения. Хранение схем само по себе не подтверждает их актуальность и не отменяет будущую проверку расписаний.

- Вернуться к общему кешу ответов поставщиков после измерения повторных обращений и появления потребности переиспользовать ответы между построениями или заявками.
- Предусмотреть ключ полного запроса, исходное время наблюдения, разные TTL по типам данных в рамках условий поставщика и объединение одновременных одинаковых запросов.
- Не кешировать ошибки как успешную пустую выдачу; сохранять признак неполноты ответа. Проверить истечение TTL, отмену ожидания, параллельные запросы и недоступность Redis.

Redis не заменяет сохранённые результаты и историю в PostgreSQL. Истечение TTL не запускает поиск: периодичностью управляет планировщик.


## Реализовано: первый этап проверки расписаний в ЛК

Сохранённые graph-схемы проверяются через Collector/Яндекс на конкретные даты; Search сохраняет результат, вкладка «Стыковки» показывает времена и причины неполноты. [Границы и запуск](ops/schedules.md).

Далее: источник длительностей наземных переездов, разрешение часовых поясов аэропортов для Google Flights, проверка покрытия расписаний и цен РФ, структурирование Gemini-схем перед проверкой, управляемый повтор проверки. Актуальные тарифы на группу пассажиров и наличие мест пока не подключены. Обязательная оптимизация внешних запросов и отложенный Redis остаются отдельными задачами.

Отложено: периодическая перепроверка расписаний активных заявок. Сейчас проверка выполняется один раз после построения схем, вкладка «Стыковки» только читает сохранённый результат. Обсуждался интервал 10 минут — пример, не принятое значение: при бюджете 80 запросов на проверку это до 480 обращений к Яндексу в час на каждую активную заявку, поэтому интервал и бюджет согласовать с [сокращением внешних запросов](#обязательно-сокращение-внешних-запросов). Правила устаревания, сохранения прежнего результата и защиты от запоздавших ответов — по разделу [актуальности результатов](#далее-актуальность-результатов-одной-заявки); потребуется поправка ADR 0013.
