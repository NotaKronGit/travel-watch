# План разработки

Статус: подготовлены документация, структура monorepo и первый локальный сценарий Cabinet: регистрация, вход, сессии и кабинет React Admin. Добавлены PostgreSQL в Compose, миграции и проверки, полный stage_local и workflow GitHub Actions. Поиск и другие сервисы ещё не реализованы.

## Последовательность

1. Первая форма, API подсказок, сохранение, список и просмотр своих заявок реализованы по [спецификации заявки](specs/trip-request.md): поездка в одну сторону, города, диапазон дат отправления и взрослые пассажиры. Согласован мировой охват подсказок с автоматическим наполнением справочника; импорт GeoNames реализован отдельной командой с тестовым источником без внешних запросов в CI. Завершить описание состояний заявки, контрактов заданий и событий и получения результатов кабинетом.
2. Каркас monorepo, PostgreSQL и базовая авторизация Cabinet готовы; расширять локальное окружение по мере реализации остальных компонентов.
3. Реализовать сценарий на тестовом источнике: создание заявки → Search → RabbitMQ → Collector → Kafka → Search → результат в вебе → Telegram.
4. Добавить периодические проверки, историю, условия уведомления, паузу и возобновление; проверить поведение при сбоях и повторных доставках.
5. Подключать реальные источники после проверки доступности API, ограничений и условий использования.

Работа ведётся небольшими шагами с объяснением решений: проект служит в том числе для изучения Go, распределённых систем и незнакомого пользователю React/TypeScript.

## Текущий этап: Cabinet → Kafka

Контракт `TripRequestCreated` и сохранение новой заявки вместе с событием в outbox реализованы по [ADR 0004](adr/0004-trip-request-outbox.md). Старые заявки не дополняются событиями. Следующий шаг — отдельный отправитель с подтверждением Kafka, арендой записей и повторами, затем локальное окружение и проверки доставки при сбоях. Потребитель Search будет отдельным этапом.

## Получение результатов: Cabinet → Search по gRPC с mTLS

Согласованный ориентир для первого сценария поиска; пока не реализован.

- Определить Protobuf-контракт чтения сохранённых результатов, истории цен, времени наблюдения и состояния проверки. Cabinet обращается к Search по gRPC с mTLS; frontend продолжает использовать ConnectRPC к Cabinet.
- До обращения к Search Cabinet проверяет сессию пользователя и принадлежность заявки. mTLS подтверждает идентичности сервисов; отдельно определить разрешённые методы и правила доступа, включая связь заявки с общим поиском.
- Чтение результатов не ждёт сбора предложений у поставщиков. Задания и события остаются в RabbitMQ и Kafka; ошибка Search не превращается в успешный пустой результат.
- Предусмотреть deadlines, отмену через `context`, ограниченные повторы безопасных запросов и явное состояние недоступности в интерфейсе.
- До реализации определить выпуск и обновление сертификатов, доверенный CA, проверку идентичностей сервисов и настройку локального окружения. Конкретные методы RPC и схема управления сертификатами остаются открытыми; детали принятого решения зафиксировать в ADR при проектировании контракта.

## Позже: синхронизация справочника по таймеру и проверка полноты переводов

Запланировано одним этапом; сейчас [импорт GeoNames](ops/city-catalog.md) запускается только вручную. Таймер и дополнительная защита пока не реализованы.

- Добавить периодический запуск существующего импортёра. Интервал и включение задавать через YAML/env; конкретный механизм расписания определить при реализации. Сохранить ручной запуск и исключить одновременные обновления.
- До включения таймера исправить замечание P2: сейчас минимум городов проверяется до фильтрации по русскому имени, а после неё достаточно одной записи. Корректная по формату, но неполная выгрузка переводов может привести к успешной публикации маленького набора и массовой деактивации ранее сохранённых городов.
- Проверять полноту локализованного набора после фильтрации и до записи в БД: добавить отдельный настраиваемый минимум городов с русским именем. Значение порога определить при реализации; дополнительно рассмотреть ограничение резкого сокращения относительно предыдущего успешного импорта.
- При отклонении снимка сохранять предыдущий справочник и его метаданные без изменений. Предусмотреть видимый статус ошибки и время последнего успешного обновления.
- Добавить тесты на полный исходный список с одним русским названием, срабатывание и границы порога, сохранение предыдущего набора при отказе и успешное обновление полноценным снимком. Тесты и CI продолжают использовать фиксированные данные без скачивания GeoNames.

## Позже: резервный источник географического справочника

Отложено до обновления по таймеру и проверки полноты данных. Сейчас при ошибке импорта сохраняется последний успешный справочник в БД; автоматическое переключение между источниками не реализовано.

- Выбрать резервный источник стран, регионов и городов, проверить покрытие, локализацию, лицензию и ограничения. Добавить адаптер через существующий интерфейс `catalog.Source`.
- Определить сопоставление идентификаторов между источниками с сохранением внутренних UUID и связей с заявками. Различия названий и покрытия не должны создавать дубли или массово деактивировать города.
- Определить условия переключения и возврата к основному источнику, приоритет данных и правила разрешения расхождений. Настройки задавать через YAML/env; происхождение и версию данных сохранять явно.
- Публиковать резервный снимок только после проверки полноты и корректности. Если ни один источник не дал подходящих данных, сохранять последний успешный справочник и показывать ошибку обновления.
- Проверить недоступность источников, неполные снимки, конфликтующие записи, повторное переключение и сохранение ссылок из заявок. Тесты и CI используют фиксированные данные без внешних загрузок.

## Позже: Telegram-уведомление о входе с нового IP

Запланировано после реализации Notification и привязки Telegram к аккаунту; пока не реализовано.

- Уведомлять привязанный Telegram об успешном входе с ранее неизвестного IP. Изменение IP при смене сети или использовании VPN само по себе не означает взлом аккаунта.
- Cabinet определяет новый адрес и сохраняет событие вместе с успешным созданием сессии через outbox. Notification получает событие через Kafka и отвечает за доставку, повторы и защиту от дублирования. Сбой Telegram не должен мешать входу.
- Определить, что считать новым IP, как долго помнить адреса, как получать адрес за доверенным proxy и подавлять повторные уведомления. Также определить состав сообщения, настройки пользователя и срок хранения данных о входах.
- Проверить повторную доставку события, недоступность Telegram и отсутствие привязки. Не добавлять таблицы и интеграцию заранее, до реализации этого этапа.

## Позже: двухфакторная аутентификация (TOTP)

TOTP отложен до завершения базового сценария регистрации, входа и серверных сессий. Вернуться к этому этапу перед публичным запуском.

- Добавить возможность включить TOTP в настройках аккаунта с подтверждением подключения.
- Предусмотреть защиту секрета, резервные одноразовые коды, восстановление доступа и безопасное отключение второго фактора.
- Если появится панель администратора с доступом к чужим данным, сделать MFA обязательной до открытия такого доступа.
- Изменения БД добавить отдельной миграцией при реализации; заранее поля TOTP не создавать.

## Проверки и развёртывание

Подготовлен CI в GitHub Actions: форматирование, Buf lint, go vet, Go-тесты с race detector, типы/тесты/сборка frontend, воспроизводимость генерации контрактов, интеграционные и браузерные сценарии, сборка Docker-образов. Workflow начнёт выполняться после публикации ветки и открытия PR. На старте проверяется весь проект; выбор проверок по изменённым сервисам возможен позже с учётом зависимостей.

После успешных проверок push в main workflow публикует образы с commit SHA в GHCR. Локальное развёртывание выполняется через `make stage-local-up`: сборка, миграции, запуск и health checks. Удалённый CD отложен. Для будущих миграций сохранять обратную совместимость. Общий pipeline должен допускать независимый деплой сервисов. Сначала Docker Compose; отдельные ресурсы для БД и брокеров и Kubernetes — по необходимости.

Добавлен режим `make dev-up` для скачивания готовых образов без сборки; после публикации обоих образов CI обновляет `dev-latest`. Настройки и команды — в [инструкции dev](ops/dev-images.md).

Команды локального запуска и проверок описаны в [инструкции разработки](ops/local-development.md). Публикация образов в GHCR и удалённое развёртывание ещё не выполнялись.

До публичного запуска: подтверждение email, восстановление пароля, MFA, HTTPS и настройка защиты входа с учётом proxy/реплик.
