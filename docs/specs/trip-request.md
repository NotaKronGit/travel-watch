# Создание заявки и выбор городов

Статус: согласованы поля первого сценария, мировой охват подсказок и автоматическое наполнение справочника вместо ручного списка. Реализован отдельный импорт GeoNames с тестовым источником и атомарным сохранением справочника. Реализованы страница `/trips/create`, API подсказок и сохранение заявки в Cabinet. Поиск и доставка заявки в Search пока не реализованы.

## Согласованный первый сценарий

Пользователь с активной сессией создаёт заявку на поездку в одну сторону:

- город отправления;
- город назначения;
- первая и последняя допустимые даты отправления;
- число взрослых пассажиров.

Диапазон относится к отправлению всей поездки, а не к датам пребывания. Обе границы включены; одинаковые даты означают отправление в один конкретный день. Система подбирает прямой вылет или одну пересадку: поезд + самолёт либо самолёт + самолёт, по [правилам маршрутов](route-building.md). Дети, обратная поездка и условия уведомления не входят в первую форму.

Подсказки охватывают города по всему миру; список не заполняется вручную. Географический охват формы шире начального покрытия поиска. Доступность города в форме не подтверждает наличие перевозок: предложения должны поступать от источников поиска. Пока источники не подключены, нельзя обозначать выбранное направление как поддерживаемое для реального поиска.

## Поведение формы

Поля «Откуда» и «Куда» работают как поиск с выбором результата. Подсказка содержит название города, регион при необходимости и страну: одинаковые названия не должны создавать неоднозначность. Отдельный обязательный выбор страны не нужен; фильтр по стране можно добавить при расширении покрытия.

После ввода минимум двух символов frontend запрашивает подсказки с небольшой задержкой, отменяет предыдущий запрос и не позволяет устаревшему ответу заменить новые результаты. Поддерживаются выбор клавиатурой и очистка. Изменение текста после выбора сбрасывает ID: произвольный текст не становится выбранным городом.

Загрузка, отсутствие совпадений и недоступность справочника показываются разными состояниями. При ошибке пользователь может повторить запрос. Ошибка сохранения не очищает заполненные поля; повтор после неопределённого результата не должен создавать дубликат заявки.

Сервер получает ID городов, даты и число взрослых. Он заново проверяет сессию, существование и актуальность городов, различие отправления и назначения, корректность диапазона и числа пассажиров. Покрытие поставщиков проверяется отдельно при запуске поиска; неизвестное покрытие не считается поддержкой. Выбор из подсказки не заменяет серверную проверку. Владелец заявки определяется по сессии, а не из параметров frontend.

## Источник справочника

Команда `make cities-sync` импортирует мировой справочник GeoNames в PostgreSQL Cabinet. [GeoNames](https://www.geonames.org/export/) предоставляет выгрузки географических данных по лицензии CC BY с указанием источника. Названия и варианты написания импортируются заранее; ввод пользователя не вызывает обращения к внешнему API. Версию и происхождение импортированных данных нужно сохранять, атрибуцию — показывать в интерфейсе и документации данных.

По умолчанию используется `cities500.zip`: населённые пункты с населением более 500 человек и некоторые административные центры. Это мировой охват, но не все населённые пункты. `countryInfo.txt` содержит страны и их коды, основной файл городов — варианты названий и часовые пояса. Русские названия городов и стран импортируются из `alternateNamesV2` в `name_ru`; города без перевода пропускаются до записи в БД. Исходное `name` сохраняется для сопоставления и поиска. Варианты написания сохраняются для будущего поиска. Форматы и критерии включения описаны в [документации выгрузок](https://download.geonames.org/export/dump/readme.txt).

Импорт выполняется отдельной командой, а не при запуске веб-сервиса. Настройки и проверки описаны в [инструкции импорта](../ops/city-catalog.md). Повторная загрузка обновляет записи по ID источника без дубликатов и ручного перечисления городов. Проверенная загрузка публикуется целиком; ошибка скачивания или разбора не заменяет рабочий справочник пустым. Исчезнувшие записи нельзя каскадно удалять вместе с заявками: их нужно сохранять для существующих ссылок, исключая из нового выбора. Расписание обновлений определяется при реализации, отдельный постоянно работающий сервис для импорта не требуется.

Cabinet хранит свой справочник и выдаёт подсказки через `TripService.SearchCities`. Поиск начинается с двух символов, работает по префиксу русского отображаемого названия и возвращает не более 10 активных городов, сначала наиболее населённые. Подпись показывает название страны серым цветом рядом с городом; коды стран и регионов скрыты. Справа показывается необязательный код IATA из GeoNames, связанный с самой записью города. Коды аэропортов не переносятся на города по близости. При нескольких различных актуальных кодах код не показывается; отсутствие кода не исключает город. Для полного покрытия нужна отдельная связь городов с транспортным справочником. Для первого этапа отдельный сервис справочника не нужен. У города есть устойчивый внутренний ID, ссылка на запись источника, код страны, название, варианты написания и признак доступности в форме. Изменение названия не меняет идентичность города и ранее созданные заявки.

Город, вокзал и аэропорт — разные сущности. GeoNames не подтверждает поддержку поставщика и не заменяет его транспортный справочник. Коды станций, аэропортов и городов конкретных поставщиков сопоставляются отдельно при подключении источников. Межсервисные контракты должны передавать явно согласованные идентификаторы; другие сервисы не читают таблицы Cabinet.

Публичный Nominatim не подходит для подсказок по мере ввода: его [правила](https://operations.osmfoundation.org/policies/nominatim/) запрещают autocomplete. Авиационный справочник одного поставщика также не покрывает автоматически железнодорожную часть маршрута.

## Оставшиеся решения перед реализацией

- Частота обновления справочника; пока импорт запускается вручную.
- Горизонт дат и ограничения поставщиков определяются при подключении поиска. Сейчас принимаются корректные даты от сегодняшнего дня по часовому поясу города отправления; отдельный предел глубины не задан.
- Отмена с сохранением истории и личная заметка реализованы. Изменение маршрута, возобновление и управление поиском пока не реализованы.

Контракт события создания заявки и атомарная запись в outbox реализованы по [ADR 0004](../adr/0004-trip-request-outbox.md). Доставка в Kafka реализована; потребитель Search и запуск поиска — следующие шаги, описанные в [roadmap](../roadmap.md).

## Сохранение и проверки

`TripService.CreateTrip` сохраняет в `trip_requests` владельца из сессии, UUID двух городов, включительный диапазон календарных дат и число взрослых от 1 до 9. Даты проверяются по часовому поясу отправления. Уведомления, обратная поездка и дети пока не поддерживаются.

Ключ `request_id` генерируется frontend для конкретного набора параметров. Повтор с тем же ключом и параметрами возвращает прежний ID; изменение параметров с тем же ключом отклоняется. Блокировка на пользователя и ключ защищает одновременные повторы. Форма сохраняет ключ для повтора при ошибке сети в рамках открытой страницы; после перезагрузки страницы он не сохраняется.

Все RPC проверяют сессию. Общая HTTP-обвязка применяет same-origin/CSRF-проверку, ограничение тела и таймаут к AuthService и TripService. Новая заявка и бинарное Protobuf-событие сохраняются в одной транзакции в `trip_requests` и `outbox_events`. Ошибка записи события откатывает заявку. Повторы не меняют сохранённый снимок городов и не создают второго события; ранее созданные заявки не дополняются событиями. Отдельный режим `publish-outbox` отправляет записи в настроенную Kafka с повторами; брокер и отправитель включены в stage_local/dev Compose. Search не реализован, интерфейс продолжает показывать «Сохранена, поиск ещё не запущен».

Миграция `00008_trip_outbox.sql` создаёт таблицу и права приложения. Её откат удаляет накопленные события. Интеграционные тесты проверяют атомарность, параллельные повторы, неизменность события после обновления справочника и отсутствие автоматического заполнения событий для старых заявок.

Проверки: `make check`, `make test-int`, `npm --prefix frontend run test:e2e`. Интеграционные тесты используют синтетические города в отдельной схеме; браузерные тесты формы подменяют API и не скачивают GeoNames. Проверяются фильтрация неактивных городов, повтор сохранения, недопустимые даты, сбой подсказок, сброс выбранного ID при редактировании текста и мобильная ширина.

Поля дат обозначены как «Самая ранняя дата выезда» и «Самая поздняя дата выезда». Перед ними объясняется, что это диапазон возможного выезда в одну сторону, а не даты туда и обратно.

Фоновая проверка сессии при возврате на вкладку не размонтирует форму. При временной ошибке проверки сохраняются поля и ключ повторного сохранения; подтверждённое отсутствие сессии приводит к переходу на вход.

Названия регионов показываются рядом со страной, в том числе после выбора города. Они импортируются из `admin1CodesASCII.txt` и переводятся через `alternateNamesV2`; при отсутствии перевода используется исходное название региона. Технические коды регионов не отображаются.

## Список и просмотр заявок

`/trips` показывает собственные заявки от новых к старым, по 20 на страницу. После создания открывается `/trips/:id`; страницу можно открыть по прямой ссылке и перезагрузить. Отображаются маршрут, страны и регионы, включительный диапазон выезда, число взрослых, дата создания и номер заявки. Статус приходит из API: новая заявка — «Сохранена, поиск ещё не запущен», отменённая — «Отменена». «Выполняется» и «Завершена» подготовлены для Search и пока автоматически не назначаются.

`ListTrips` принимает неотрицательный offset и возвращает has_more; сортировка по created_at и ID обеспечивает устойчивый порядок при равном времени создания. Добавление новых заявок между запросами страниц может сдвинуть offset. `GetTrip` принимает ID; оба метода ограничивают SQL-запрос владельцем из сессии. Для чужого и отсутствующего ID возвращается одинаковый NotFound. Неактивный город остаётся видимым в ранее сохранённой заявке; названия читаются из текущего справочника, не из исторического снимка.

Пустой список, загрузка, ошибка API с повтором и отсутствие заявки имеют отдельные состояния. Проверки включают изоляцию двух пользователей, чтение с неактивным городом, страницы списка, переход после сохранения и перезагрузку прямой ссылки.


## Отмена и комментарий

В карточке владелец может отменить активную заявку после подтверждения. При ошибке доступен повтор; при успехе кнопка отмены исчезает. Заявка остаётся в списке и карточке, статус меняется на «Отменена». Повтор отмены безопасен. Для чужой или отсутствующей заявки API возвращает одинаковый NotFound.

`CancelTrip` сохраняет cancelled_at и `TripRequestCancelled` атомарно. `GetTrip` и `ListTrips` возвращают статус, комментарий и время отмены. Отдельный UpdateTripComment меняет одну личную заметку до 2000 символов, в том числе у отменённой заявки; комментарий не попадает в Kafka. После успешной отмены карточка перечитывается, чтобы показать серверное время отмены без перезагрузки; несохранённый черновик заметки остаётся в форме. При сбое чтения статус остаётся отменённым и доступно повторное обновление карточки. При ошибке сохранения введённый текст сохраняется в форме. Заметка доступна в карточке после создания заявки.

Правила будущих переходов, порядка доставки событий и обновления — в [ADR 0005](../adr/0005-trip-lifecycle.md).
