# Первый этап Cabinet: аккаунт и сессия

Объём: локальный рабочий сценарий регистрации, входа, просмотра собственного аккаунта и выхода. React Admin предоставляет интерфейс; Go проверяет доступ и работает с PostgreSQL. Заявки, подтверждение email, восстановление пароля и TOTP не входят в этот этап. До публичного запуска нужно реализовать подтверждение email и восстановление пароля и вернуться к MFA.

## Поведение

- Email обрезается по краям и приводится к нижнему регистру; для первого этапа поддерживаются ASCII-адреса с доменом. Уникальность обеспечивает PostgreSQL.
- Пароль: минимум 15 Unicode-символов, максимум 1024 UTF-8 байта; не обрезается и не нормализуется. Хеш Argon2id с индивидуальной случайной солью, 19 MiB памяти, 2 итерации, 1 поток.
- Успешные регистрация и вход создают сессию без скользящего продления; в поставляемой конфигурации срок — 7 суток. Регистрация пользователя и создание сессии выполняются одной транзакцией.
- В cookie находится случайный 256-битный токен, в БД — его SHA-256. Cookie: HttpOnly, SameSite=Strict, Path=/; для HTTPS требуется Secure, отключение разрешено только для локального HTTP.
- Повторный вход заменяет текущую сессию браузера; сессии других устройств остаются. Выход удаляет сессию в БД и cookie, повторный выход допустим.
- Истёкшая сессия не даёт доступ; в поставляемой конфигурации сервер раз в час удаляет истёкшие записи.
- Интерфейс различает отсутствие сессии и сбой проверки: `Unauthenticated` ведёт на вход без запроса выхода; недоступность API показывает отдельный экран с повтором проверки, скрывая кабинет. После восстановления API можно продолжить с прежней сессией.
- При ошибке явного выхода интерфейс сообщает, что завершение сессии не подтверждено, и позволяет повторить выход. Успешный переход на страницу входа выполняется только после ответа сервера.
- Неверный пароль и неизвестный email дают одинаковую ошибку входа. Дубликат регистрации отклоняется; в текущем локальном варианте это позволяет определить наличие email.
- RPC принимает только POST с точным Origin и заголовком X-Travel-Watch-CSRF: 1. Vite проксирует API с того же origin, CORS не используется.
- Вход и регистрация в поставляемой конфигурации: не более 10 попыток в минуту на адрес соединения; не более 4 одновременных операций хеширования. Лимит хранится в памяти одного процесса, ограничен 4096 адресами. Перезапуск его сбрасывает; работа за production proxy и общие лимиты реплик требуют отдельного решения.

Срок сессии, очистка, лимиты и Secure-cookie задаются через [конфигурацию Cabinet](../ops/configuration.md). Изменение срока действует на новые сессии.

## Данные и контракт

`users`: UUID, нормализованный email, хеш пароля, created_at, updated_at. `sessions`: хеш токена, пользователь, created_at, expires_at. Роль cabinet_owner применяет миграции; cabinet_app получает только необходимые права на таблицы и не меняет схему.

[Protobuf-контракт](../../api/proto/travelwatch/cabinet/v1/auth.proto): Register, Login, Logout, GetCurrentUser. Получение чужого пользователя по ID не предоставляется. dataProvider появится при добавлении ресурсов заявок; на этом этапе нужен только authProvider.

## Критерии готовности

- Новый пользователь регистрируется и попадает в кабинет с собственным email.
- После обновления страницы вход сохраняется; после выхода или истечения сессии профиль недоступен.
- Повторная регистрация, неверный пароль, чужой Origin, отсутствие CSRF-заголовка и превышение лимита обрабатываются явно.
- Параллельная регистрация одного email создаёт только одного пользователя.
- Миграции повторно применяются без повторного создания таблиц; роль приложения не имеет DDL-прав.
- Пройдены Go-тесты, интеграционные проверки PostgreSQL, сборка frontend и браузерный сценарий.
