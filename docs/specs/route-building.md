# Построение маршрута: первый шаг

Статус: реализованы модели, интерфейс источника и построение транспортных кандидатов в `services/search/internal/routes` на синтетическом наборе Иваново → Паттайя. К обработчику Kafka и пользовательскому API алгоритм пока не подключён. Реальные транспортные источники, предложения и расписания отсутствуют.

## Границы

Начинаем с формирования кандидатов без запросов к поставщикам, Kafka/RabbitMQ и изменений статусов Cabinet. Кандидат означает «этот вариант нужно проверить», а не наличие билетов.

Поддерживаемые формы первого алгоритма:

- прямой рейс между подходящими аэропортами отправления и назначения;
- поезд до одного города пересадки, затем прямой рейс;
- два перелёта с пересадкой в одном аэропорту или с явным переездом между разными аэропортами;
- необходимые наземные переезды до/между транспортными узлами и до конечного города.

MVP допускает максимум два основных участка: прямой самолёт, поезд + самолёт или самолёт + самолёт. Наземные переезды идут отдельными участками. Билеты считаются отдельными; защищённость пересадки не подтверждается.

## Что моделируем

| Понятие | Содержание |
| --- | --- |
| Город | Точка отправления или назначения из заявки; не заменяет аэропорт или вокзал |
| Транспортный узел | Конкретный аэропорт или вокзал со своим ID, городом и часовым поясом; коды поставщиков хранятся отдельно |
| Связь города с узлом | Возможность добраться до аэропорта/вокзала, с происхождением данных и условиями переезда |
| Транспортное направление | Возможность искать поезд или прямой рейс между узлами; источник, покрытие и период применимости |
| Кандидат маршрута | Упорядоченная последовательность участков, которую предстоит проверить |
| Предложение | Конкретный поезд/рейс на дату, времена, тариф, цена с валютой, пассажиры и время наблюдения |
| Собранный маршрут | Совместимые предложения с учётом переездов и ограничений |

GeoNames и поле IATA в Cabinet не являются источником транспортных направлений. Один город может обслуживаться несколькими аэропортами, один аэропорт — несколькими городами. Сопоставлять по одному названию города нельзя. Search использует снимок заявки и собственный источник транспортных связей, не читает таблицы Cabinet.

## Тестовый пример Иваново → Паттайя

Для первого набора выбираем Иваново: есть [местный аэропорт](https://www.ivanovoaero.ru/air/obshchie-svedeniya/) и [железнодорожный вокзал](https://ivanovo.dzvr.ru/). Два внешних аэропорта-кандидата — Шереметьево (Москва) и Стригино (Нижний Новгород).

Это приближение к условию равноудалённости: расстояния по прямой порядка 250 и 190 км соответственно ([географический ориентир](https://www.kupibilet.ru/gid/rossiia/ivanovo)). Они сопоставимы, но не равны. Эти числа не являются расстояниями по дороге или временем поездки и не используются как расписание. Первый алгоритм не использует расстояния для отбора: оба аэропорта рассматриваются по связям. Проверки сравнения времени и стоимости будут добавлены с предложениями.

Ниже исключительно синтетическая схема. Наличие аэропорта не подтверждает нужные рейсы. Все направления, цены, длительности и расписания тестового набора вымышлены; узлы получают тестовые ID отдельно от реальных кодов.

```text
Иваново
  ├─ местный аэропорт → прямой тестовый рейс → аэропорт назначения
  ├─ вокзал → поезд до Москвы → переезд в Шереметьево → прямой рейс
  └─ вокзал → поезд до Нижнего Новгорода → переезд в Стригино → прямой рейс
Каждый вариант завершается переездом из аэропорта назначения в Паттайю.
```

Оба города пересадки должны обнаруживаться из связей тестового источника. Нельзя выбирать только ближайший аэропорт или зашивать Москву в алгоритм. Включены также перелёты из местного аэропорта до Москвы и Нижнего Новгорода с последующим рейсом. Это вымышленные направления тестового источника.

Первый тест проверяет обнаружение пяти базовых ветвей, затем повторяет поиск без прямого местного направления: остаются два варианта поезд + самолёт и два самолёт + самолёт. Для будущей сборки предложений предусматриваются случаи, когда выигрывает Москва, Нижний Новгород или местный вылет; более близкий аэропорт может проиграть из-за расписания, долгого переезда или цены. Для проверки неизвестного покрытия отдельно убираются данные источника, а не только сами направления.

## Выбор кандидатов

1. Получить подходящие узлы для исходного и конечного городов. Если сопоставления отсутствуют, вернуть «недостаточно данных», а не «билетов нет».
2. Найти известные прямые авиационные направления между ними.
3. От аэропортов назначения пройти назад по известным прямым авиационным направлениям и получить возможные аэропорты вылета.
4. Для каждого такого аэропорта проверить возможность доехать поездом из исходного города до конкретного вокзала и наличие переезда вокзал → аэропорт. Также проверить первый перелёт до этого аэропорта или другого аэропорта того же города с явной связью переезда.
5. Сформировать последовательности участков, исключить циклы и одинаковые последовательности узлов и видов транспорта. Предложения разных перевозчиков пока не склеивать: их ещё нет на этом шаге.
6. Ограничить объём перебора параметрами алгоритма. При достижении лимита явно обозначить неполное покрытие; порядок отбора сделать воспроизводимым. Текущий порядок: прямые кандидаты, затем поезд + самолёт, два перелёта в одном аэропорту и два перелёта со сменой аэропорта; внутри — стабильная сортировка связей по типу и ID узлов. Это технический порядок, не рейтинг по цене или времени.

Для первого алгоритма источник — небольшой фиксированный тестовый набор. Это не ручной производственный справочник мира. Доступ к связям отделяется интерфейсом от алгоритма; реальный адаптер выбирается после изучения возможностей поставщика.

Если реальный источник умеет искать только заданную пару узлов, потребуется отдельный источник направлений или ограниченный набор городов пересадки. Если он умеет выдавать направления, можно использовать его для формирования кандидатов. Эти возможности пока не подтверждены.

## Проверка предложений — следующий шаг

После выбора кандидатов потребуется запросить предложения на даты и собрать совместимые сочетания. Успешный пустой ответ, сбой и отсутствие покрытия источника — разные результаты.

Диапазон заявки относится к началу всей поездки в часовом поясе исходного города, включительно. Следующий участок может отправляться на следующий день; нельзя ограничивать даты всех участков тем же диапазоном. Правило учёта начального переезда до вокзала/аэропорта требуется определить до расчёта времён.

Для стыковки проверяется:

```text
прибытие предыдущего транспорта
+ время выхода/получения багажа
+ время наземного переезда
+ запас на задержку
+ время до отправления следующего транспорта для регистрации/посадки
≤ отправление следующего транспорта
```

Каждый запас учитывается один раз. Сравнения выполняются по абсолютному времени, календарные даты отображаются в местных часовых поясах. Кроме минимального запаса нужны предел ожидания и максимальная длительность всей поездки; их значения пока открыты. Неизвестная длительность переезда не равна нулю и не позволяет подтвердить стыковку.

Неизвестная цена переезда не равна нулю: сумма известных билетов показывается как неполная стоимость. До правил пересчёта валют и сопоставления тарифов нельзя объявлять один маршрут самым дешёвым среди несопоставимых вариантов.

## Проверки первого алгоритма

- Прямой кандидат найден без обязательной пересадки.
- Кандидат поезд + самолёт найден через данные о связях, без зашитого города пересадки.
- Несколько аэропортов одного города рассматриваются отдельно.
- Нет подходящего переезда между вокзалом и аэропортом — составной кандидат не подтверждается как связный.
- Отсутствие данных отличается от отсутствия направлений в полном тестовом наборе.
- Дубликаты связей не создают дубликаты кандидатов; нет циклов.
- Лимит перебора даёт воспроизводимый результат с признаком неполного покрытия.
- Два перелёта поддерживаются; три основных участка исключаются.
- Пересадка в разных аэропортах требует явной направленной связи переезда. Без неё кандидат не строится и отклоняется общим валидатором.

Проверки расписаний, перехода через полночь, часовых поясов, минимальной стыковки и частичных цен добавляются вместе со сборкой предложений.

## Что ещё определить

- Реальные источники узлов, направлений, расписаний и цен; их покрытие и идентификаторы.
- Граница подходящего аэропорта: допустимое время/расстояние переезда и источник этих данных.
- Ограничения перебора, ожидания, общей длительности и запасов на пересадку.
- Начало поездки внутри исходного города и детализация наземных переездов.
- Приоритеты «быстрее», «дешевле», «меньше пересадок» и модель полной стоимости.
- Как различать единый билет и самостоятельную стыковку отдельных билетов при подключении реального источника; сейчас билеты считаются отдельными.

Типы, источник и алгоритм реализованы. Следующий небольшой шаг — модель конкретных предложений и проверка временной совместимости на синтетических расписаниях. Планировщик, контракты Collector и RabbitMQ добавляются после определения входов и выходов этого алгоритма.


## Контракт реализованного алгоритма

`routes.Build(ctx, source, query, limits)` возвращает последовательности направленных участков. Query содержит ID исходного и конечного городов. Даты и пассажиры остаются в заявке; этот шаг проверяет только топологию и не подтверждает применимость направлений на конкретную дату.

Source отдаёт снимок со списками городов, узлов и связей, именем источника, признаком тестовых данных и полнотой покрытия запроса. Дубликаты узлов, неизвестные конечные точки и несовместимые типы связей отклоняются. Повторяющиеся связи удаляются. Переезды вокзал → аэропорт и аэропорт → другой аэропорт допускаются внутри одного города; доступ города к обслуживающему его аэропорту может пересекать административную границу.

Result отдельно содержит `SourceIncomplete`, `MissingMapping` и `LimitReached`. Даже полный пустой результат означает только отсутствие кандидатов в заданном наборе связей и политике MVP, а не отсутствие билетов во всём мире. Частичный результат может содержать найденные кандидаты. Ошибка источника возвращается ошибкой, а не пустым успехом.

Лимиты обязательны и передаются вызывающим кодом: `MaxNodes` (города вместе с транспортными узлами), `MaxLinks` (входные связи до удаления дублей), `MaxSteps` (рассмотренные связи при обходе) и `MaxCandidates`. Слишком большой снимок отклоняется; исчерпание обхода помечает результат как неполный. Достижение ровно MaxCandidates не считается усечением, если дополнительных кандидатов нет. Лимиты тестов — 100 узлов, 100 связей, 1000 шагов и 20 кандидатов; это не настройки производственного покрытия. При подключении алгоритма к процессу лимиты будут добавлены в YAML/env Search.

Проверка без PostgreSQL, Kafka и сетевых запросов:

```sh
go test -race ./services/search/internal/routes/...
go test -v ./services/search/internal/routes -run '^TestIvanovo$'
```

Общие `make test` и `make check` также включают эти тесты. Отдельного запуска алгоритма из Cabinet и отображения кандидатов в интерфейсе пока нет.

## Сменные алгоритмы и сравнение

Интерфейс `Planner.Plan(ctx, snapshot, query, limits)` отделяет построение кандидатов от получения транспортных данных. Текущая реализация — `GraphPlanner`. `Engine{Source, Planner}.Build(...)` позволяет выбрать реализацию; прежняя функция `Build` использует GraphPlanner по умолчанию.

`Compare` загружает снимок один раз, передаёт каждому из двух алгоритмов отдельную копию и запускает их последовательно с отдельным таймаутом на загрузку и на каждую попытку. Реализации обязаны соблюдать context; адаптер внешнего API должен передавать его в сетевые вызовы. Принудительное завершение произвольного кода, игнорирующего context, не гарантируется.

Общий валидатор проверяет результаты любого алгоритма: существование каждого участка в исходном снимке, начало и конец заявки, непрерывность, отсутствие циклов, допустимые сочетания MVP и предел количества кандидатов. Повторы одинаковых маршрутов удаляются. Источник, признак синтетических данных и неполнота исходного покрытия берутся из исходного снимка, а не из ответа алгоритма. Неверный кандидат отклоняет всю попытку; второй алгоритм всё равно может дать собственный успешный результат.

Comparison содержит результат, ошибку и длительность каждой попытки, а при успехе обеих — общие кандидаты и варианты только слева/справа. Сравнение идёт по последовательности узлов и видов транспорта, независимо от порядка выдачи и дублей. `Compared=false` означает, что сравнение множеств не выполнено из-за ошибки, а не равенство или отсутствие маршрутов. Признаки неполного покрытия сохраняются отдельно у каждой попытки: совпадение кандидатов не доказывает полноту поиска. Автоматического объединения, выбора победителя или fallback нет.

LLM-адаптер пока отсутствует. Для него нужно выбрать поставщика и модель, определить формат ответа, лимиты токенов и стоимости и проверять ответы тем же валидатором. Выдуманные моделью направления не могут стать подтверждёнными связями снимка. Эвристическая реализация обязана помечать своё покрытие неполным, если не гарантирует полный перебор. При подключении к процессу Search выбор реализации и режим сравнения будут задаваться через YAML/env; сейчас это библиотечный интерфейс без пользовательского переключателя.

Пример выбора и сравнения на уровне кода:

```go
engine := routes.Engine{Source: source, Planner: routes.GraphPlanner{}}
result, err := engine.Build(ctx, query, limits)

// alternate — любая другая реализация Planner; реального LLM-адаптера пока нет.
comparison, err := routes.Compare(ctx, source, routes.GraphPlanner{}, alternate, query, limits, timeout)
```


## Разные аэропорты прилёта и вылета

Местный и международный рейсы могут обслуживаться разными физическими аэропортами. Каждый имеет собственный ID: общий город не объединяет узлы. Отдельный тест добавляет шестой кандидат: Иваново → тестовый аэропорт прилёта Москвы → наземный переезд в тестовое Шереметьево → аэропорт назначения → Паттайя. Без связи межаэропортового переезда остаются пять базовых кандидатов.

Для стыковки в одном аэропорту отдельного переезда нет, но время на смену терминала, получение багажа и регистрацию всё равно потребуется проверить на этапе расписаний. Тип местного или международного рейса не доказывает наличие направления или достаточный запас времени.
