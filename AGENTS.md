# Инструкции для работы с Travel Watch

## Контекст и стиль работы

Travel Watch — учебный Go-проект для поиска составных поездок и отслеживания цен. Краткое описание находится в [README.md](README.md).

- Общайся с пользователем по-русски, объясняй решения простым языком.
- Двигайся последовательно, небольшими законченными шагами. Пользователь хочет понимать устройство проекта; React и TypeScript для него новые.
- Выполняй текущую задачу полностью, но не расширяй её до реализации следующих этапов без запроса. Задача на документацию не подразумевает создание приложения.
- Различай реализованное, согласованный ориентир и открытые вопросы. Не описывай планируемые возможности как работающие.
- Рутинные обратимые действия в рамках запроса выполняй без повторного согласования. Существенные изменения согласованной архитектуры сначала объясни и обсуди.

## Документация и решения

- Перед изменениями изучи относящиеся к задаче документы: [продукт](docs/product.md), [архитектуру](docs/architecture.md), [план разработки](docs/roadmap.md) и описание затрагиваемого сервиса в `docs/services`.
- Для задач запуска, Docker и CI/CD изучи инструкции в `docs/ops`: [локальная разработка](docs/ops/local-development.md), [stage_local](docs/ops/stage-local.md), [готовые dev-образы](docs/ops/dev-images.md). Выбирай окружение по цели проверки: запуск опубликованного образа не проверяет текущие локальные правки.
- Соблюдай описанные границы сервисов и правила корректности данных. Не заполняй открытые вопросы неявными предположениями.
- Храни справочную информацию в соответствующем документе, не дублируй её в README и инструкциях агентам. README должен оставаться краткой точкой входа.
- Существенные принятые архитектурные решения фиксируй в `docs/adr` по мере появления. Нерешённые вопросы оставляй явно обозначенными.
- Обозначай тестовые данные. Утверждения об актуальной доступности перевозок и возможностях API подтверждай данными источников.

## Реализация и проверки

- В Go используй ограниченную конкурентность, `context`, таймауты внешних операций и корректное завершение процессов. Не запускай неограниченные горутины для заданий.
- Добавляй проверки, соответствующие изменению. Для обработки сообщений особенно важны повторная доставка, сбои и частичные результаты; для маршрутов — время и допустимость стыковки.
- Используй существующие команды из Makefile и документации. Указывай только фактически выполненные проверки; проверка конфигурации CI не подтверждает успешный запуск workflow или публикацию образов.
- Для изменений только в документации проверяй согласованность текста, ссылки и diff; запуск приложения не требуется.
- По итогам кратко сообщай, что изменено, что проверено и какие существенные вопросы остались.
- Обновляй соответствующие документы при изменении возможностей, структуры и команд; в README поддерживай актуальные статус, ссылки и инструкции запуска. Не добавляй инфраструктуру только ради соответствия будущему плану.

## Репозиторий и внешние действия

- Работай непосредственно в основной папке проекта `/Users/notakron/twt/travel-watch`. Не создавай временные копии проекта или worktree без явного запроса пользователя. Если запись ограничена, запроси доступ к основной папке.
- Сохраняй чужие изменения. Перед правками проверяй состояние рабочего дерева.
- Не создавай коммиты, не отправляй изменения в remote, не публикуй образы и не выполняй деплой без запроса пользователя, охватывающего соответствующее действие.
- Не изменяй существующие SSH-ключи и настройки GitHub: SSH уже настроен.
- Не добавляй секреты, токены и реальные учётные данные в код, документацию, логи или примеры. Для конфигурации используй безопасные placeholders.
- Другие проекты могут служить образцом подхода, если пользователь разрешил их изучить. Это не разрешение копировать бизнес-код, секреты или приватные данные.
